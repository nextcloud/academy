## Why this matters

In M2 you told Nextcloud your app exists. In this module you tell it what to *do* when someone visits it. The controller is where your app's logic begins — every HTTP request that reaches your app lands in a controller method. Understanding how that happens, and why Nextcloud's controller pattern works the way it does, is the foundation everything else in the course builds on.

---

## The request lifecycle — what happens when someone visits your app

Before writing any code it's worth understanding the sequence Nextcloud runs through for every request involving your app:

1. nginx/Apache receives the HTTP request and hands it to `index.php`
2. Nextcloud bootstraps — loads enabled apps, calls their `register()` methods
3. The router matches the URL against `appinfo/routes.php`
4. The matched route name (`page#index`) is resolved to a controller class and method (`PageController::index()`)
5. The DI container resolves `PageController`'s constructor dependencies and instantiates it
6. The method is called with any URL parameters injected as arguments
7. The method returns a `Response` object
8. Nextcloud serialises the response and sends it back

Your job as an app developer is to write steps 4–7. Nextcloud handles everything else.

> **Why this matters for debugging:** When something goes wrong, knowing which step failed tells you where to look. A 404 means step 3 failed (route not matched). A 500 with a class-not-found error means step 4–5 failed (namespace or autoloading problem). A blank page usually means step 7 returned the wrong response type. The log file will point you towards the right step.

## Concepts

### Controllers

A controller is a PHP class that extends `OCP\AppFramework\Controller`. Each public method that handles a request is called an **action**. Controllers live in `lib/Controller/` and follow the naming convention `SomethingController.php`.

Create `lib/Controller/PageController.php`:

```php
<?php

declare(strict_types=1);

/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */

namespace OCA\Pinboard\Controller;

use OCA\Pinboard\AppInfo\Application;
use OCP\AppFramework\Controller;
use OCP\AppFramework\Http\Attribute\FrontpageRoute;
use OCP\AppFramework\Http\Attribute\NoAdminRequired;
use OCP\AppFramework\Http\Attribute\NoCSRFRequired;
use OCP\AppFramework\Http\JSONResponse;
use OCP\AppFramework\Http\TemplateResponse;
use OCP\IRequest;
use Psr\Log\LoggerInterface;

class PageController extends Controller {

    public function __construct(
        IRequest $request,
        private readonly LoggerInterface $logger,
    ) {
        parent::__construct(Application::APP_ID, $request);
    }

    #[NoAdminRequired]
    #[NoCSRFRequired]
    #[FrontpageRoute(verb: 'GET', url: '/')]
    public function index(): TemplateResponse {
        $this->logger->debug('Pinboard index page requested');
        return new TemplateResponse(Application::APP_ID, 'main');
    }
}
```

Several things to unpack here.

---

### Dependency injection in practice

Notice the constructor takes `IRequest` and `LoggerInterface` as parameters — it doesn't instantiate them with `new`. This is **dependency injection (DI)**: rather than a class creating its own dependencies, it declares what it needs and something else provides them. That "something else" is the **DI container** — a central registry that knows how to build every service in the system.

When a request comes in and Nextcloud needs to call your controller method, the container:

1. Looks at your controller's constructor parameters
2. Resolves each one — finding or building the right implementation
3. Constructs your controller with those resolved dependencies
4. Calls your method

You never call `new PageController(...)` yourself. The container does it, and it has access to things you don't — the current database connection, the active user session, the correct logger for your app.

**Why not just use `new`?** Two reasons:

First, testability. In a unit test you can pass a mock `LoggerInterface` that records what was logged, then assert your controller logged the right things. If your controller called `new Logger()` internally, you couldn't intercept it.

Second, in Nextcloud's multi-tenant environment, services like `LoggerInterface` carry context — which app is running, which user is active. Getting the logger via injection gives you a pre-configured instance that already knows it's writing on behalf of `pinboard`. Instantiating your own would lose that context.

**`IRequest`** is always the first constructor parameter for controllers — it's required by the parent class. Everything after it is your app's own dependencies.

**Constructor promotion** (`private readonly LoggerInterface $logger`) is PHP 8.x syntax that declares and assigns the property in one line. It's the idiomatic style in NC34 apps — you'll see it throughout the Nextcloud codebase.

> **The OCP namespace:** Both `IRequest` and `LoggerInterface` (the PSR-3 interface, which Nextcloud's logger implements) are imported from `OCP\` or standard PSR interfaces, never from `OC\`. This is the rule from M2: only ever import from `OCP\` in your app code. Nextcloud's internal `OC\` classes can change between releases without warning.

---

### Security attributes

The three attributes above `index()` are security declarations:

**`#[NoAdminRequired]`** — the default for any controller method is admin-only access. This attribute lifts that restriction so any authenticated user can reach the endpoint. Authentication is still required — this is not a public page. For that you'd use `#[PublicPage]`, which removes the login requirement entirely. Since Pinboard is a personal app for all logged-in users, every endpoint needs `#[NoAdminRequired]`.

**`#[NoCSRFRequired]`** — every non-GET request to a Nextcloud controller is checked for a CSRF token by default, and `index()` is the one place that can't have one yet: it renders the very first page load, before any token exists in the browser to send back. Without this attribute here, loading the page fails with a CSRF error. Any endpoint whose job is to serve the initial HTML shell needs it; endpoints called *after* the page has loaded (like the API routes you'll add in Module 4) rely on `@nextcloud/axios` attaching the token instead, and should not have this attribute.

**`#[FrontpageRoute]`** — marks this as a regular (non-OCS) route and defines the URL and HTTP verb. This is the NC29+ attribute-based routing syntax. It replaces the need to declare this route in `routes.php` — though both approaches work and `routes.php` is still valid.

> **A note on the older annotation syntax:** You may encounter older Nextcloud code using `@NoAdminRequired` in PHPDoc comments rather than PHP 8 attributes. Those still work but are deprecated — use the attribute syntax for all new code.

---

### Responses

Your controller method must return an instance of `OCP\AppFramework\Http\Response`. Nextcloud provides several response types:

**`TemplateResponse`** — renders a PHP template from your `templates/` directory. The two arguments are the app ID and the template name (without `.php`). This is what a page request returns.

**`JSONResponse`** — serialises a PHP array or object to JSON and sets the correct `Content-Type` header. This is what API endpoints return. You'll use this extensively from M4 onwards.

**`DataResponse`** — a more structured version of `JSONResponse` used with OCS API controllers. Covered in Intermediate M3.

**`RedirectResponse`** — redirects to another URL.

For now, `index()` returns a `TemplateResponse`. The template it references (`main`) doesn't exist yet — we'll create it in a moment.

---

### The template

Create `templates/main.php`:

```php
<?php
/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */
/** @var \OCP\IL10N $l */
/** @var \OCP\Defaults $theme */
?>
<div id="app-pinboard">
    <h2><?php p($l->t('Pinboard')); ?></h2>
    <p><?php p($l->t('Your pins will appear here.')); ?></p>
</div>
```

Two things to note:

**`p()`** is Nextcloud's output escaping function — it prints a string while escaping HTML entities. **Never use `echo` or `print` in templates.** Using `p()` prevents XSS vulnerabilities. The only exception is `print_unescaped()`, which exists for cases where you're outputting already-sanitised HTML and know what you're doing. Default to `p()` for everything.

**`$l->t()`** wraps a string for translation. Even if you're not planning to translate your app right now, wrapping strings from day one means you never have to go back and retrofit it. The `$l` variable is injected into templates automatically by `TemplateResponse`.

---

### Logging

The `LoggerInterface` your controller receives is a PSR-3 compatible logger. It has five levels that map to Nextcloud's numeric log levels:

| Method | Level | When to use |
|---|---|---|
| `$this->logger->debug()` | 0 | Detailed flow tracing — only useful during development |
| `$this->logger->info()` | 1 | Normal events worth recording — user actions, state changes |
| `$this->logger->warning()` | 2 | Something unexpected but recoverable |
| `$this->logger->error()` | 3 | An operation failed |
| `$this->logger->critical()` | 4 | Something is seriously broken |

Since you set `loglevel` to `0` in M1's exercise, all five levels will appear in your log file during development.

You can include context in log messages using placeholder interpolation:

```php
$this->logger->info('User {user} created pin {url}', [
    'user' => $userId,
    'url' => $pinUrl,
]);
```

The `{user}` and `{url}` placeholders are replaced with the values from the context array. This is cleaner than string concatenation and makes log parsing easier.

> **Don't log sensitive data.** User passwords, session tokens, and personal data should never appear in log entries — even at debug level. The log file is readable by anyone with server access.

### Adding a JSON endpoint

Now add a second method to `PageController` — a simple API endpoint that will eventually return the user's pins. For now it returns an empty array:

```php
#[NoAdminRequired]
#[FrontpageRoute(verb: 'GET', url: '/pins')]
public function getPins(): JSONResponse {
    $this->logger->debug('Fetching pins for user');
    return new JSONResponse([]);
}
```

Also notice we're *not* adding this to `routes.php` — the `#[FrontpageRoute]` attribute handles the registration. You can verify it's registered:

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- routes | grep pinboard
```

You should see both `pinboard.page.index` and `pinboard.page.get_pins` listed.

---

### Why not put everything in routes.php?

Both approaches — `routes.php` and PHP attributes — are valid in NC34. The attribute approach keeps the route declaration next to the method it applies to, which makes it easier to reason about. The `routes.php` approach gives you a single file where all routes are visible at once, which is useful for complex apps with many endpoints.

For this course we'll use attributes as the primary approach since it's the modern convention, but `routes.php` remains the right tool for routes that need more complex configuration (requirements, defaults, postfixes) or when you want a bird's-eye view of all routes in one place.

**1. Create the controller and template**

Create `lib/Controller/PageController.php` and `templates/main.php` with the code from the Concepts section above. Your file tree should now look like:

```
pinboard/
├── appinfo/
│   ├── info.xml
│   └── routes.php
├── lib/
│   ├── AppInfo/
│   │   └── Application.php
│   └── Controller/
│       └── PageController.php        ← new
└── templates/
    └── main.php                      ← new
```

**2. Visit the app**

Navigate to `http://nextcloud.local/index.php/apps/pinboard/` logged in as `admin`. You should see a plain page with "Pinboard" as a heading and "Your pins will appear here." — no styling yet, but the request/response cycle is working.

**3. Check the log**

In your log-tailing terminal you should see a debug entry from your controller:

```bash
# Run from: ~/nextcloud-docker-dev/
tail -f workspace/server/data/nextcloud.log | python3 -m json.tool
```

Look for `"message":"Pinboard index page requested"` with `"app":"pinboard"`. This confirms your controller ran and the logger context is correct.

**4. Test the JSON endpoint**

Visit `http://nextcloud.local/index.php/apps/pinboard/pins` in your browser, or use curl:

```bash
curl -u admin:admin http://nextcloud.local/index.php/apps/pinboard/pins
```

Expected response: `[]` — `JSONResponse` returns your data directly without any envelope.

**5. Verify routes are registered**

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- routes | grep pinboard
```

You should see at minimum:


## Common problems

**500 error — "Class OCA\Pinboard\Controller\PageController not found"**  
The namespace in `PageController.php` doesn't match the file path. Check that:
- The `namespace` declaration is exactly `OCA\Pinboard\Controller;`
- The file is at `lib/Controller/PageController.php` (capital C in Controller)
- The class name is `PageController`

All three must align for Nextcloud's classloader to find your class.

**Page loads but shows a Nextcloud error about a missing template**  
The template name in `new TemplateResponse(Application::APP_ID, 'main')` must match the filename in `templates/` exactly — `templates/main.php`. Check capitalisation.

**`p()` is undefined**  
You're not inside a `TemplateResponse`-rendered template. The `p()` function is only available in PHP templates rendered by Nextcloud's template engine. It's not available in controllers or services.

**curl returns a 401**  
Your endpoint requires authentication and `curl` isn't sending credentials. Add `-u admin:admin` to the curl command, or test in the browser while logged in.

**Routes command shows no pinboard routes**
The attribute-based routes aren't being picked up. Check that:
- You have `use OCP\AppFramework\Http\Attribute\FrontpageRoute;` at the top of the controller
- The `#[FrontpageRoute(...)]` attribute is on the correct line (directly above the method, not above another attribute)

## NC34 notes

The `#[FrontpageRoute]` and `#[ApiRoute]` attributes were added in NC29 and are the preferred approach in NC34. The `routes.php` array approach still works and is not deprecated — use whichever suits the situation.

The constructor promotion syntax (`private readonly LoggerInterface $logger`) requires PHP 8.0+. Since NC34 requires PHP 8.2+ this is always safe to use.
