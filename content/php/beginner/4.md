## Why this matters

Up until now Pinboard's JSON endpoint returns a hardcoded empty array. In this module you give the app memory — a database table that persists pins between requests. You'll also learn the pattern Nextcloud uses to separate data access from business logic, which keeps your code testable and your database queries safe by default.

---

## Concepts

### How Nextcloud manages database schema

Nextcloud apps don't create tables by running SQL directly. Instead they use **migrations** — versioned PHP classes that describe schema changes. Nextcloud tracks which migrations have run and executes new ones automatically when the app is installed or updated.

This approach has two advantages. First, it makes upgrades safe — Nextcloud can take a user from any old version of your app to any new version by running the migrations they haven't seen yet. Second, it works across SQLite, MySQL/MariaDB, and PostgreSQL without you writing database-specific SQL.

Migrations live in `lib/Migration/` and are named `Version<AppVersion>Date<Timestamp>.php`. The timestamp is what determines execution order.

---

### Creating the migration

Generate the migration file first:

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- migrations:generate pinboard 0200
```

The `0200` argument maps to app version `0.2.x` following the 3-digit convention: `0.1.x → 0100`, `0.2.x → 0200`, `1.0.x → 1000`, `2.34.x → 2034`. This lets you introduce migrations in separate branches for different Nextcloud versions without filename collisions — leave enough space between numbers.

> **If this fails with "Could not write to ... lib/Migration/Version...php":** see the permissions fix in Common problems below — this is an environment issue, not a mistake in your code.

This creates a file at `lib/Migration/Version0200Date<timestamp>.php`. The generated file contains scaffolding for all three migration methods — `preSchemaChange`, `changeSchema`, and `postSchemaChange`. For this migration you only need `changeSchema`, so delete the other two methods and implement `changeSchema` as shown below:

```php
<?php

declare(strict_types=1);

/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */

namespace OCA\Pinboard\Migration;

use Closure;
use OCP\DB\ISchemaWrapper;
use OCP\DB\Types;
use OCP\Migration\Attributes\CreateTable;
use OCP\Migration\Attributes\ColumnType;
use OCP\Migration\IOutput;
use OCP\Migration\SimpleMigrationStep;

#[CreateTable(
    table: 'pinboard_pins',
    description: 'Stores user pins'
)]
class Version0200Date20250101000000 extends SimpleMigrationStep {

    public function changeSchema(IOutput $output, Closure $schemaClosure, array $options): ISchemaWrapper {
        /** @var ISchemaWrapper $schema */
        $schema = $schemaClosure();

        if (!$schema->hasTable('pinboard_pins')) {
            $table = $schema->createTable('pinboard_pins');

            $table->addColumn('id', Types::BIGINT, [
                'autoincrement' => true,
                'notnull' => true,
                'length' => 20,
                'unsigned' => true,
            ]);
            $table->addColumn('user_id', Types::STRING, [
                'notnull' => true,
                'length' => 64,
            ]);
            $table->addColumn('url', Types::STRING, [
                'notnull' => true,
                'length' => 4000,
            ]);
            $table->addColumn('title', Types::STRING, [
                'notnull' => false,
                'length' => 255,
            ]);
            $table->addColumn('favourited', Types::SMALLINT, [
                'notnull' => true,
                'default' => 0,
                'unsigned' => true,
            ]);
            $table->addColumn('created_at', Types::BIGINT, [
                'notnull' => true,
                'length' => 20,
            ]);

            $table->setPrimaryKey(['id']);
            $table->addIndex(['user_id'], 'pinboard_pins_user_id');
        }

        return $schema;
    }
}
```

Several things to understand here:

**`if (!$schema->hasTable(...))`** — always guard table creation with this check. If the migration runs twice (or if your app is installed on an instance that somehow already has the table) it won't crash.

**Table naming** — prefix your table with your app ID: `pinboard_pins` not just `pins`. Nextcloud shares a single database across all apps — an unprefixed `pins` table would collide with any other app that had the same idea.

> **The `oc_` prefix:** When you inspect the actual database, your table will be called `oc_pinboard_pins` rather than `pinboard_pins`. Nextcloud automatically prepends a configurable prefix (defaulting to `oc_`) to every table name — you never write or reference this prefix in your code. The migration schema API, `QBMapper`, and `getTableName()` all handle it transparently. This is why `getTableName()` in the mapper is always preferable to hardcoding the string — if an instance uses a custom prefix, the method returns the correct full name automatically.

**`Types::BIGINT` for `id`** — always use `BIGINT` for primary keys, not `INTEGER`. This future-proofs against large datasets. The `unsigned` flag doubles the effective range.

**`Types::BIGINT` for `created_at`** — store timestamps as Unix epoch integers (seconds since 1970), not as `DATETIME` strings. This avoids timezone complications across different database backends. Rather than calling `time()` directly, Nextcloud apps use `ITimeFactory` from the DI container — it makes time testable by allowing tests to control the clock. You'll see this injected in the controller shortly.

**`Types::STRING` and length** — `Types::STRING` maps to different underlying column types depending on the length you specify. Lengths up to 255 produce a `VARCHAR(n)` — fixed maximum, indexable. Longer lengths (like the 4000 we use for `url`) produce a `TEXT`/`CLOB`/`LONGTEXT` depending on the database backend, since most databases don't allow `VARCHAR` beyond a certain threshold. This is handled transparently by Nextcloud's DBAL abstraction, but it has one practical consequence: **columns mapped to `TEXT` cannot be indexed directly**. This is why the `user_id` column (length 64, safely a `VARCHAR`) can have an index, but the `url` column (length 4000, a `TEXT`) cannot. When you need to index a string column, keep its length at 255 or below.

**`user_id` length of 64** — Nextcloud user IDs are strings, not integers, and can be up to 64 characters. Always use this length for any column storing a Nextcloud user ID.

**`Types::SMALLINT` for booleans** — while Doctrine DBAL exposes a `boolean` type, it behaves inconsistently across database backends and introduces subtle conversion bugs. The Nextcloud convention is therefore `Types::SMALLINT` with a default of `0`, which stores `0` (false) or `1` (true) as a small integer and works identically everywhere. The mapping to PHP `bool` is handled in the entity via `addType('favourited', 'boolean')`, which tells the mapper to cast the value on read. Without this cast, `$pin->getFavourited()` would return the string `"0"` or `"1"` rather than `false` or `true`. You'll see this in the entity definition below.

**`notnull`** — when `true`, the database enforces that this column must always have a value — `NULL` is not permitted. Setting `default => 0` alongside `notnull => true` means every new row gets `0` automatically if no value is provided, satisfying the constraint without requiring the caller to always pass the field explicitly. When `notnull` is `false` (as with `title`), the column is optional and a missing value is stored as `NULL` rather than an empty string — reflected in the entity as a nullable PHP type (`?string $title`).

**The index on `user_id`** — every query you write will filter by `user_id` (to scope data to the current user). Without an index, those queries do a full table scan. Add the index now.

**Migration attributes** — the `#[CreateTable(...)]` attribute added in NC30 lets admins see what a migration does before running it. Always add these.

Once the migration file is complete, bump the version in `appinfo/info.xml` from `0.1.0` to `0.2.0`:

```xml
<version>0.2.0</version>
```

Do this **after** writing the migration — if you bump the version first and reload Nextcloud before the migration file is ready, Nextcloud may record the version change without running any migration, and your table won't be created.

> **If you need to edit a migration after it's been run:** Nextcloud records which migrations have executed. If you edit a migration that's already been applied to your dev database, the change won't run — Nextcloud thinks it's already done. Since our migration uses `if (!$schema->hasTable(...))`, you must always drop the table first — otherwise `hasTable()` returns `true` and the entire `changeSchema` body is skipped silently:
> ```bash
> # Run from: ~/nextcloud-docker-dev/
> docker compose exec database-mysql mysql -u root -pnextcloud nextcloud -e "DROP TABLE oc_pinboard_pins;"
> ```
> Alternatively, spin up phpMyAdmin with `docker compose up -d phpmyadmin` and access it at `http://phpmyadmin.local`.
>
> Once the table is dropped, choose how to re-run the migration:
>
> - **`migrations:execute`** (debug mode only) — force-runs a specific migration regardless of whether it's been recorded as executed:
>   ```bash
>   # Run from: ~/nextcloud-docker-dev/
>   ./scripts/occ.sh nextcloud -- migrations:execute pinboard 0200Date20250101000000
>   ```
>   The version argument is the class name without the `Version` prefix.
>
> - **Delete the migration record** — remove the entry from the `oc_migrations` table for your migration, then bump `info.xml` to `0.2.1` — or, if you have already done so, another increment of `+1`. Nextcloud will treat the migration as new and run it on the next page load.
>   ```bash
>   # Run from: ~/nextcloud-docker-dev/
>   docker compose exec database-mysql mysql -u root -pnextcloud nextcloud -e "DELETE FROM oc_migrations WHERE app='pinboard' AND version='0200Date20250101000000';"
>   ```

### The Entity

An entity is a PHP class representing a single row in your table. Create `lib/Db/Pin.php`:

```php
<?php

declare(strict_types=1);

/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */

namespace OCA\Pinboard\Db;

use OCP\AppFramework\Db\Entity;

/**
 * @method string getUserId()
 * @method void setUserId(string $userId)
 * @method string getUrl()
 * @method void setUrl(string $url)
 * @method string|null getTitle()
 * @method void setTitle(?string $title)
 * @method bool getFavourited()
 * @method void setFavourited(bool $favourited)
 * @method int getCreatedAt()
 * @method void setCreatedAt(int $createdAt)
 */
class Pin extends Entity implements \JsonSerializable {

    protected string $userId = '';
    protected string $url = '';
    protected ?string $title = null;
    protected bool $favourited = false;
    protected int $createdAt = 0;

    public function __construct() {
        $this->addType('userId', 'string');
        $this->addType('url', 'string');
        $this->addType('title', 'string');
        $this->addType('favourited', 'boolean');
        $this->addType('createdAt', 'integer');
    }

    #[\Override]
    public function jsonSerialize(): array {
        return [
            'id' => $this->getId(),
            'userId' => $this->userId,
            'url' => $this->url,
            'title' => $this->title,
            'favourited' => $this->favourited,
            'createdAt' => $this->createdAt,
        ];
    }
}
```

Four things to note:

**`id` is inherited** — `Entity` provides an `$id` field automatically. Don't declare it again.

**Column name mapping** — database columns use `snake_case` (`user_id`, `created_at`) but entity properties use `camelCase` (`userId`, `createdAt`). The mapper handles this conversion automatically. The mapping is mechanical: `user_id` → `userId`, `created_at` → `createdAt`.

**`addType()`** — tells the mapper how to cast column values. Without this, everything comes back as a string. Note that `addType` uses the camelCase property name, not the database column name.

**Getters and setters are generated automatically** — `Entity` uses PHP magic methods. You never write `getUserId()` or `setUserId()` — they exist automatically for every property you declare. However, IDEs and static analysis tools can't see magic methods, so the convention is to declare them explicitly as `@method` PHPDoc tags on the class. This is what you see above — one `@method` line per getter and per setter, with the correct return and parameter types. The methods are still generated at runtime by `Entity`; the PHPDoc tags are purely for tooling.

**`jsonSerialize()` is required if you want to return the entity as JSON** — and this one catches almost everybody, because it fails silently rather than with an error.

`Entity` does *not* implement `JsonSerializable`, and its only public property is the inherited `$id`. Your own properties are `protected`. When PHP's `json_encode()` is handed a plain object, it serialises **public properties only** — so returning a `Pin` directly would produce:

```json
{"id":42}
```

No `url`, no `title`, no `createdAt`. The request succeeds, the response looks like valid JSON, and the data is simply absent. Nothing warns you.

Implementing `JsonSerializable` fixes this by telling `json_encode()` exactly what to output. Two details in the code above:

- **`implements \JsonSerializable`** — the interface declares a single method, `jsonSerialize()`, which returns whatever should be encoded in place of the object. Returning an array of your fields gives you full control over the shape of your API response, including omitting fields you don't want to expose.
- **`#[\Override]`** — added because `jsonSerialize()` is defined by the interface you just implemented. The attribute tells PHP to verify that: if you typo the name as `jsonSerialise()`, PHP raises a compile-time error instead of silently defining an unrelated method that never gets called. It requires PHP 8.3, which is Nextcloud 34's minimum anyway. This matches how server apps do it — see `Absence` in the DAV app or `VersionEntity` in Files Versions.

This is the standard pattern in Nextcloud apps: an explicit `jsonSerialize()` per entity, listing the fields the API returns. Note that it also decouples your API from your database schema — renaming a column doesn't have to change your JSON.

### The Mapper

The mapper is where database queries live. It extends `QBMapper`, which provides safe parameterised queries and automatic entity mapping. Create `lib/Db/PinMapper.php`:

```php
<?php

declare(strict_types=1);

/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */

namespace OCA\Pinboard\Db;

use OCP\AppFramework\Db\DoesNotExistException;
use OCP\AppFramework\Db\QBMapper;
use OCP\DB\QueryBuilder\IQueryBuilder;
use OCP\IDBConnection;

/**
 * @template-extends QBMapper<Pin>
 */
class PinMapper extends QBMapper {

    public function __construct(IDBConnection $db) {
        parent::__construct($db, 'pinboard_pins', Pin::class);
    }

    /**
     * @return Pin[]
     */
    public function findAll(string $userId): array {
        $qb = $this->db->getQueryBuilder();
        $qb->select('*')
            ->from($this->getTableName())
            ->where($qb->expr()->eq('user_id', $qb->createNamedParameter($userId, IQueryBuilder::PARAM_STR)))
            ->orderBy('created_at', 'DESC');
        return $this->findEntities($qb);
    }

    /**
     * @throws DoesNotExistException
     */
    public function findById(int $id, string $userId): Pin {
        $qb = $this->db->getQueryBuilder();
        $qb->select('*')
            ->from($this->getTableName())
            ->where($qb->expr()->eq('id', $qb->createNamedParameter($id, IQueryBuilder::PARAM_INT)))
            ->andWhere($qb->expr()->eq('user_id', $qb->createNamedParameter($userId, IQueryBuilder::PARAM_STR)));
        return $this->findEntity($qb);
    }
}
```

Several things to understand:

**`$this->getTableName()`** — always use this rather than hardcoding the table name string. The parent constructor stores it; using the method means you only ever change the name in one place.

**`createNamedParameter()`** — this is how you safely pass values into queries. Never use string concatenation or interpolation to build a query — that's how SQL injection happens. `createNamedParameter()` creates a bound parameter that the database driver handles safely.

**Always filter by `user_id`** — every query must include the current user's ID as a condition. `findById` checks both `id` and `user_id`. This prevents user A from accessing user B's pins by guessing a pin ID. This pattern is so important it's worth repeating: **never query solely by `id`**. Always scope to the user.

**`findEntities()` vs `findEntity()`** — `findEntities()` returns an array (zero or more results). `findEntity()` returns exactly one result or throws `DoesNotExistException`. Use `findEntity()` when you expect a single row and want an exception if it's missing.

**`@template-extends QBMapper<Pin>`** — the Psalm type annotation tells static analysis that this mapper works with `Pin` entities. Include it — it enables type-safe return values without runtime overhead.

**`insert()`, `update()`, `delete()`** are inherited from `QBMapper` — you don't need to write them. They work on entity objects directly: `$this->insert($pin)`, `$this->update($pin)`, `$this->delete($pin)`.

### Wiring it together in the controller

Now update `PageController` to actually use the mapper. Inject `PinMapper` and the current user ID:

```php
<?php

declare(strict_types=1);

/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */

namespace OCA\Pinboard\Controller;

use OCA\Pinboard\AppInfo\Application;
use OCA\Pinboard\Db\Pin;
use OCA\Pinboard\Db\PinMapper;
use OCP\AppFramework\Controller;
use OCP\AppFramework\Http\Attribute\FrontpageRoute;
use OCP\AppFramework\Http\Attribute\NoAdminRequired;
use OCP\AppFramework\Http\JSONResponse;
use OCP\AppFramework\Http\TemplateResponse;
use OCP\AppFramework\Utility\ITimeFactory;
use OCP\IRequest;
use Psr\Log\LoggerInterface;

class PageController extends Controller {

    public function __construct(
        IRequest $request,
        private readonly LoggerInterface $logger,
        private readonly PinMapper $pinMapper,
        private readonly ITimeFactory $timeFactory,
        private ?string $userId,
    ) {
        parent::__construct(Application::APP_ID, $request);
    }

    #[NoAdminRequired]
    #[FrontpageRoute(verb: 'GET', url: '/')]
    public function index(): TemplateResponse {
        $this->logger->debug('Pinboard index page requested');
        return new TemplateResponse(Application::APP_ID, 'main');
    }

    #[NoAdminRequired]
    #[FrontpageRoute(verb: 'GET', url: '/pins')]
    public function getPins(): JSONResponse {
        $pins = $this->pinMapper->findAll($this->userId);
        return new JSONResponse($pins);
    }

    #[NoAdminRequired]
    #[FrontpageRoute(verb: 'POST', url: '/pins')]
    public function createPin(string $url, ?string $title = null, bool $favourited = false): JSONResponse {
        $pin = new Pin();
        $pin->setUserId($this->userId);
        $pin->setUrl($url);
        $pin->setTitle($title);
        $pin->setFavourited($favourited);
        $pin->setCreatedAt($this->timeFactory->getTime());

        $this->pinMapper->insert($pin);
        $this->logger->info('Pin created for user {user}', ['user' => $this->userId]);
        return new JSONResponse($pin);
    }
}
```

**`?string $userId`** — the current user's ID is injected as a nullable string. It can be `null` if the request is unauthenticated (e.g. a public page) — since we have `#[NoAdminRequired]` on all methods and not `#[PublicPage]`, it will always be set in practice. The nullable type is still correct because the DI container may inject `null` for unauthenticated contexts; your `#[NoAdminRequired]` attribute is what guarantees it won't be `null` when your method runs.

**`ITimeFactory`** — rather than calling `time()` directly, Nextcloud apps use `ITimeFactory::getTime()`. The reason is testability: in unit tests you can inject a mock `ITimeFactory` that returns a fixed timestamp, making time-dependent behaviour deterministic. Calling `time()` directly would make those tests unreliable. Use `ITimeFactory` anywhere you need the current time.

**`new Pin()` + setters** — for `insert()`, create a new entity, set its properties using the generated setters, then pass it to the mapper. The `id` field is left unset — the database assigns it on insert.

**`insert()` returns the entity** — `QBMapper::insert()` returns the inserted entity with its new `id` populated. That's what we return to the caller in `createPin()`.

**4. Create a pin**

```bash
curl -u bob:bob \

  -H "Content-Type: application/json" \
  -d '{"url":"https://nextcloud.com","title":"Nextcloud"}' \
  http://nextcloud.local/index.php/apps/pinboard/pins
```

Expected response: the full pin as JSON, with the `id` the database assigned and the `createdAt` timestamp the controller set — every field listed in the entity's `jsonSerialize()`:

```json
{"id":1,"userId":"admin","url":"https://nextcloud.com","title":"Nextcloud","favourited":false,"createdAt":1753800000}
```

If you see only `{"id":1}`, your `Pin` is missing the `jsonSerialize()` method from the Concepts section — see the note there on why an entity returns nothing without it.

**5. Retrieve your pins**

```bash
curl -u bob:bob http://nextcloud.local/index.php/apps/pinboard/pins
```

Expected response: a JSON array containing the pin you just created.

**6. Verify user scoping**

Create a pin as alice, then confirm each user only sees their own:

```bash
curl -u alice:alice \
  -X POST \
  -H "Content-Type: application/json" \
  -d '{"url":"https://docs.nextcloud.com","title":"NC Docs"}' \
  http://nextcloud.local/index.php/apps/pinboard/pins

curl -u bob:bob http://nextcloud.local/index.php/apps/pinboard/pins
curl -u alice:alice http://nextcloud.local/index.php/apps/pinboard/pins
```

Bob should see only his pin. Alice should see only hers. If either sees both, the `user_id` filter is missing from `findAll`.

## Common problems

**`migrations:generate` fails with "Failed to generate new migration step. Could not write to ... lib/Migration/Version...php"**
This is a file-permission mismatch, not a bug in your code. The `apps-extra/` directory is bind-mounted straight from your host machine, so the `pinboard` folder you cloned or unzipped is owned by your host user. But `./scripts/occ.sh` runs commands inside the container as `www-data`, which is a different user — and by default it has no write access to a directory it doesn't own. Fix it once per app by making the directory writable by any user inside the container:
```bash
# Run from: ~/nextcloud-docker-dev/
docker compose exec nextcloud chmod -R o+w apps-extra/pinboard
```
Then re-run the `migrations:generate` command. You'll only need to do this once — new files created inside `lib/Migration/` after this point inherit write access from the directory.

**`migrations:generate` produces an error about debug mode**
The `migrations:generate` command is only available in debug mode. Verify debug mode is on:
```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- config:system:get debug
```
If it returns `false`, set it: `./scripts/occ.sh nextcloud -- config:system:set debug --value=true --type=bool`

**Migration runs but the table doesn't appear**
Check that your `changeSchema` method returns `$schema`. A common mistake is forgetting the `return` statement — without it the schema change is discarded silently.

**`DoesNotExistException` when creating a pin**
You're calling `findEntity()` somewhere when the row doesn't exist. For `createPin()`, make sure you're calling `insert()` not `findEntity()`.

**Setters don't exist / IDE shows "method not found"**
This is expected — `Entity` generates getters and setters via magic methods. Your IDE won't know about them. The methods do exist at runtime. If you need IDE completion, you can add `@method` annotations to your entity class, but it's not required.

**User scoping not working — users can see each other's pins**
Check that every query in `PinMapper` includes an `andWhere` clause filtering by `user_id`. A query that only filters by `id` is a security vulnerability — any authenticated user can access any pin by guessing the ID.

**`curl` returns 500 after adding `PinMapper` to the constructor**
The DI container can't resolve `PinMapper`. Check that:
- `PinMapper` extends `QBMapper`
- The namespace is exactly `OCA\Pinboard\Db`
- The file is at `lib/Db/PinMapper.php`

## NC34 notes

The `#[CreateTable]` and other migration attributes were added in NC30 and are available in NC34. They're optional but good practice — include them.

The `Types::` constants (`Types::BIGINT`, `Types::STRING` etc.) replaced the older `IQueryBuilder::PARAM_*` type strings for schema definitions. Always use `Types::` for column definitions in migrations.

**Snowflake IDs:** Since NC33, Nextcloud recommends using Snowflake IDs rather than auto-incrementing integers as primary keys. The `OCP\AppFramework\Db\SnowflakeAwareEntity` class extends `Entity` and handles Snowflake ID generation transparently — you don't need to call any generator yourself. This is covered in Intermediate Module 1 — The OCP Contract, once you have more context about the OCP API layer. For now, auto-increment is perfectly functional and the simpler concept to start with.

Migrating an existing auto-increment primary key to Snowflake IDs is also a good exercise for Advanced students — it requires a carefully sequenced multi-step migration (add new column, populate with generated IDs, swap the primary key, drop the old column) without data loss. This is covered in Advanced Module 10 — Architecture Patterns for Complex Apps.
