## Why this matters

Everything built across M1–M7 lives in your development environment. This module gets it out into the world. The Nextcloud app store is the primary distribution channel — it's how administrators discover, install, and update apps directly from the Nextcloud interface, without touching the server filesystem.

The release process has four distinct stages:

1. **Prepare** — bump the version, update the changelog, fill in the store metadata in `info.xml`
2. **Build** — create a production build from a clean clone with development files removed
3. **Sign** — sign the clean build with your private key so Nextcloud can verify its integrity on install
4. **Submit** — host the tarball, upload the release to the store, push the git tag

The order matters. Signing must happen after building and cleaning, and submitting must happen after signing. This module walks through each stage in sequence.

## Concepts

### Semantic versioning

Every release needs a version number following [semantic versioning](https://semver.org/) — `MAJOR.MINOR.PATCH`. The rules for Nextcloud apps:

- **Patch** (`0.1.0 → 0.1.1`) — bug fixes, translation updates, documentation. No new features, no breaking changes.
- **Minor** (`0.1.0 → 0.2.0`) — new features, adding support for a new Nextcloud or PHP version, dropping EOL versions.
- **Major** (`0.1.0 → 1.0.0`) — breaking changes, dropping support before EOL. Signals to admins that they should read the release notes carefully before upgrading.

Pinboard is currently at `0.2.0` from Module 4. `0.x.y` is a perfectly valid release version — it signals the app's API may still be evolving. Use `1.0.0` when you're confident in the feature set and ready to commit to the semver contract.

The version must be bumped in four places that all need to stay in sync:

- **`appinfo/info.xml`** — the version Nextcloud and the app store read
- **`package.json`** — the version npm and build tools see
- **`package-lock.json`** — do not edit by hand; run `npm install` after updating `package.json` and it updates automatically
- **`CHANGELOG.md`** — the human-readable release notes

Commit all four together in a single "bump version to 1.0.0" commit so the history is clean.

> **Why the version matters for migrations:** Nextcloud uses the version in `info.xml` to determine whether to run your database migrations when a user updates. Incrementing the version without a migration is fine — but shipping a migration without incrementing it means it will never run on existing installations.

### The CHANGELOG

The app store reads `CHANGELOG.md` and displays the release notes for the installed version in the admin settings panel. A well-maintained changelog builds trust with administrators.

Follow the [Keep a Changelog](https://keepachangelog.com) format — it's the standard Nextcloud apps use. Each release gets a dated heading, with changes grouped under `Added`, `Changed`, `Fixed`, `Removed`, `Security`, and `Deprecated` as needed.

```markdown
# Changelog

## [Unreleased]

## 1.0.0 - 2025-06-01

### Added
- Pin URLs with optional titles
- User-scoped pin storage — each user sees only their own pins
- Vue 3 frontend with add, view, and delete pin functionality
- Code signing for app store distribution

### Changed
- Initial public release
```

### The info.xml fields that matter for the store

Before packaging, make sure `appinfo/info.xml` has all the fields the app store requires. The store validates your manifest on upload — a missing field or invalid category value will reject the submission.

```xml
<?xml version="1.0"?>
<!--
  SPDX-FileCopyrightText: 2025 Your Name
  SPDX-License-Identifier: AGPL-3.0-or-later
-->
<info xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xsi:noNamespaceSchemaLocation="https://apps.nextcloud.com/schema/apps/info.xsd">
  <id>pinboard</id>
  <name>Pinboard</name>
  <summary>Save and organise URLs in your Nextcloud</summary>
  <description><![CDATA[
Pinboard lets you save, tag and organise URLs directly in your Nextcloud interface.
Each user's pins are private to them. Built as part of the Nextcloud Developer Course.
  ]]></description>
  <version>1.0.0</version>
  <licence>agpl</licence>
  <author mail="you@example.com" homepage="https://yoursite.com">Your Name</author>
  <category>organization</category>
  <bugs>https://github.com/YOUR_USERNAME/pinboard-php/issues</bugs>
  <repository>https://github.com/YOUR_USERNAME/pinboard-php</repository>
  <dependencies>
    <php min-version="8.3"/>
    <nextcloud min-version="34" max-version="34"/>
  </dependencies>
  <navigations>
    <navigation>
      <id>pinboard</id>
      <name>Pinboard</name>
      <route>pinboard.page.index</route>
      <icon>app.svg</icon>
      <order>10</order>
    </navigation>
  </navigations>
</info>
```

Key fields:

**`summary`** — a single sentence shown in search results and the app list. Keep it under 80 characters and make it scannable.

**`description`** — shown on the app detail page. Supports basic markdown via a CDATA block. Cover what the app does, who it's for, and any notable features.

**`category`** — must be exactly one of: `auth`, `customization`, `files`, `integration`, `monitoring`, `multimedia`, `office`, `organization`, `social`, `tools`. The store will reject any other value.

**`bugs`** — where users report issues, displayed on the store listing. Link to your GitHub issues page. Required — apps without a bugs URL are harder for admins to trust.

**`repository`** — your source code URL. Required for the certificate request process.

**`min-version` / `max-version`** — the Nextcloud version range your app supports. Set `max-version` conservatively — only include versions you've actually tested against.

**Apps must not include "Nextcloud" in their name** — "Pinboard" is fine, "Nextcloud Pinboard" is not.

### Building a release

A release tarball is not your development directory. Always build from a clean clone, not your working directory. Use `npm ci` rather than `npm install` for reproducible builds.

```bash
# Clone a fresh copy — never package your working directory
git clone https://github.com/YOUR_USERNAME/pinboard-php.git pinboard-release
cd pinboard-release
git checkout v1.0.0

# Build production assets
npm ci
npm run build

# Remove everything that doesn't belong in a release
rm -rf node_modules
rm -f package-lock.json package.json webpack.js
rm -rf tests .github .gitignore
```

### Code signing

Code signing is required for all apps on apps.nextcloud.com. When a Nextcloud instance installs or updates your app, it verifies a cryptographic signature against a certificate issued by the Nextcloud Code Signing Root Authority.

**Step 1: Generate your key and CSR**

The CN (Common Name) must exactly match your app's `<id>` in `info.xml`. Never share the private key — store it in a password manager.

```bash
openssl req -nodes -newkey rsa:4096 \
  -keyout pinboard.key \
  -out pinboard.csr \
  -subj "/CN=pinboard"

mkdir -p ~/.nextcloud/certificates/
mv pinboard.key ~/.nextcloud/certificates/pinboard.key
```

**Step 2: Request your certificate**

Submit a pull request to [github.com/nextcloud/app-certificate-requests](https://github.com/nextcloud/app-certificate-requests) with your `pinboard.csr` and a link to your source repository. The signing team will return `pinboard.crt` in a few days.

```bash
mv pinboard.crt ~/.nextcloud/certificates/pinboard.crt
```

**Step 3: Sign and package**

Sign last — after removing all development files. The `integrity:sign-app` command hashes every file and signs the collection. Any change after signing invalidates the signature.

```bash
# Run from your Nextcloud server root
./occ integrity:sign-app \
  --privateKey=~/.nextcloud/certificates/pinboard.key \
  --certificate=~/.nextcloud/certificates/pinboard.crt \
  --path=/full/path/to/pinboard-release

# Rename to match app ID, then package
mv pinboard-release pinboard
tar -czf pinboard-1.0.0.tar.gz pinboard/

# Verify tarball structure — first line must be pinboard/
tar -tzf pinboard-1.0.0.tar.gz | head -5
```

### Git tagging

Tag the release before submitting. Use annotated tags for releases — they store the tagger's identity, timestamp, and message as a full git object.

```bash
git tag -a v1.0.0 -m "First public release"
git push origin v1.0.0
```

Tags serve three practical purposes: traceability (check out any tag to reproduce a bug exactly), GitHub releases (pushing a tag creates a release page automatically), and CI/CD triggers (at Advanced Module 10, a tag push will trigger the full automated release pipeline).

### App store submission

**Register your app (once):**

Go to [apps.nextcloud.com/developer/apps/new](https://apps.nextcloud.com/developer/apps/new). Paste your certificate and generate a registration signature:

```bash
echo -n "pinboard" | openssl dgst -sha512 \
  -sign ~/.nextcloud/certificates/pinboard.key | openssl base64
```

**Host the tarball:**

Attach `pinboard-1.0.0.tar.gz` to the GitHub release you created when pushing the tag. Copy the direct download URL.

**Upload the release:**

Go to [apps.nextcloud.com/developer/apps/releases/new](https://apps.nextcloud.com/developer/apps/releases/new). Provide the download URL and a release signature over the tarball:

```bash
openssl dgst -sha512 \
  -sign ~/.nextcloud/certificates/pinboard.key \
  pinboard-1.0.0.tar.gz | openssl base64
```

> **App store cache:** Nextcloud instances cache the catalogue for approximately one hour after a successful upload.

---

### Maintaining the signing certificate

- Store your private key somewhere secure — every release requires it
- Multiple maintainers: designate one release manager who holds the private key
- Lost key: submit a new CSR to app-certificate-requests and mention the loss — Nextcloud will revoke the old certificate
- Once you've signed a release, all future releases must also be signed — unsigned updates will be rejected

## Exercise: Prepare and verify a release build

Work through this checklist before every release:

- ☐ Version bumped in `appinfo/info.xml`
- ☐ Version bumped in `package.json`
- ☐ `npm install` run to sync `package-lock.json`
- ☐ `CHANGELOG.md` updated with release notes
- ☐ All four version strings match
- ☐ `info.xml` store fields complete: `summary`, `description`, `category`, `bugs`, `repository`
- ☐ `info.xml` validates against the schema
- ☐ Production build run: `npm run build`
- ☐ App tested from the production build
- ☐ Release built from a clean git clone
- ☐ Development files removed
- ☐ App signed with `integrity:sign-app`
- ☐ `appinfo/signature.json` present
- ☐ Tarball contains exactly one top-level folder named `pinboard/`
- ☐ Git tag created and pushed
- ☐ GitHub release created with tarball attached

```bash
# Validate info.xml
xmllint --noout \
  --schema https://apps.nextcloud.com/schema/apps/info.xsd \
  appinfo/info.xml

# Verify tarball structure
tar -tzf pinboard-1.0.0.tar.gz | head -5
```

## Common problems

**`integrity:sign-app` fails with "Certificate is not valid for required scope"**  
The CN in your certificate doesn't match your app ID. `pinboard` in the CSR must exactly match the `<id>` in `info.xml`.

**App store rejects with "invalid archive structure"**  
The tarball must contain exactly one top-level folder named after your app ID. Check with `tar -tzf pinboard-1.0.0.tar.gz | head` — the first line must be `pinboard/`.

**Signature verification fails on install**  
A file was modified after signing. Sign last, after all cleanup is done.

**`xmllint` validation fails**  
Usually a missing required field or invalid category value. The error message is specific.

**App doesn't appear in Nextcloud after uploading**  
Check `min-version` / `max-version` range, or the release may still be in manual review.

**Store says the app ID is already taken**  
App IDs are globally unique. Choose a different ID and update directory name, `info.xml`, PHP namespaces, route names, and database table prefixes consistently.
