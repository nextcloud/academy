## Why this matters

In M4 you added `?string $userId` to the controller constructor and Nextcloud silently injected the right value. That probably felt like magic. Understanding *how* it works — and when each approach is appropriate — is one of the most fundamental things to know about Nextcloud's DI system. It also unlocks why `#[NoAdminRequired]`, `#[PublicPage]`, and session context matter so much, and sets you up for everything in the Intermediate track that builds on identity.

---

## Concepts

### How `?string $userId` works

In M3 you saw the DI container resolve services like `LoggerInterface` and `PinMapper` by type. The `$userId` parameter is a special case of the same system — but instead of resolving by type, the container resolves it by **name**.

`DIContainer` — Nextcloud's per-app DI container — registers `userId` as a named service that resolves from the current session. When your controller constructor declares `private ?string $userId`, the container looks up the `userId` service, calls `IUserSession::getUser()` internally, and injects the result — `null` if no user is logged in, the user's UID string if they are.

**The name matters.** If you rename the parameter to `$currentUserId` or anything else, the container won't recognise it and will fail to resolve it. It must be exactly `$userId`.

---

### `IUserSession` — the explicit alternative

The `?string $userId` pattern is convenient but opaque. The explicit alternative is to inject `IUserSession` directly and call `getUser()` yourself. You won't use this in Pinboard right now — it becomes relevant when you extract service classes at Intermediate — but it's worth understanding the pattern:

```php
// Concept only — not needed in Pinboard yet

use OCP\IUserSession;

public function __construct(
    private readonly IUserSession $userSession,
) {}

private function getCurrentUserId(): string {
    $user = $this->userSession->getUser();
    if ($user === null) {
        throw new \LogicException('getCurrentUserId() called outside a user session context');
    }
    return $user->getUID();
}
```

This is more verbose but more transparent — it's obvious where the user ID comes from. It's also safer in contexts outside controllers (services, background jobs, command handlers) where the `$userId` magic parameter isn't available.

**When to use each:**

- `?string $userId` — controllers only, where the session context is guaranteed. Concise and idiomatic Nextcloud.
- `IUserSession` — services, background jobs, or anywhere the code might run without a request context. Explicit and portable.

The Pinboard controller in M4 uses `?string $userId`. For a service class you extract at Intermediate, you'd use `IUserSession` instead.

---

### What `getUID()` returns

`IUser::getUID()` returns a plain string — the user's login name, like `bob` or `alice`. This is what you store in `user_id` columns and filter on in queries. It is **not** the display name (which can be changed) and **not** a numeric ID (Nextcloud users don't have numeric IDs — the UID is the primary identifier).

---

### Session attributes and the `#[NoAdminRequired]` connection

`#[NoAdminRequired]` does two things: it allows non-admin users to call the endpoint, and it *implicitly requires a logged-in user*. Any request without a valid session gets a 401 before your controller is called.

This is why `?string $userId` is always non-null in a `#[NoAdminRequired]` controller in practice, even though the type says `?string`. The `?` covers the case where the parameter is resolved outside a request context (tests, CLI), not the case where the user isn't logged in.

The contrast:

```php
#[NoAdminRequired]     // requires session → $userId is always non-null
#[PublicPage]          // no session required → $userId may be null
// (no attribute)      // requires admin session → $userId is non-null, but only for admins
```

### Adding single-pin endpoints

So far the controller only has `getPins` (list all) and `createPin`. Now that you understand user scoping, this module adds two more endpoints — fetching and deleting a single pin — both of which require looking up by ID and verifying ownership.

Add these methods to `lib/Controller/PageController.php`, alongside the existing `getPins` and `createPin` methods. You'll also need to add the `DoesNotExistException` and `Http` imports to the top of the file:

```php
use OCP\AppFramework\Db\DoesNotExistException;
use OCP\AppFramework\Http;

#[NoAdminRequired]
public function getPin(int $id): JSONResponse {
    try {
        $pin = $this->pinMapper->findById($id, $this->userId);
        return new JSONResponse($pin);
    } catch (DoesNotExistException $e) {
        return new JSONResponse(['message' => 'Not found'], Http::STATUS_NOT_FOUND);
    }
}

#[NoAdminRequired]
public function deletePin(int $id): JSONResponse {
    try {
        $pin = $this->pinMapper->findById($id, $this->userId);
        $this->pinMapper->delete($pin);
        return new JSONResponse([]);
    } catch (DoesNotExistException $e) {
        return new JSONResponse(['message' => 'Not found'], Http::STATUS_NOT_FOUND);
    }
}
```

Then add the corresponding routes to `appinfo/routes.php`, alongside the existing `getPins` and `createPin` routes:

```php
['name' => 'pin#get_pin',    'url' => '/pins/{id}', 'verb' => 'GET'],
['name' => 'pin#delete_pin', 'url' => '/pins/{id}', 'verb' => 'DELETE'],
```

The key principle: `findById` is called with both `$id` **and** `$this->userId` before any action is taken. A pin that exists but belongs to a different user throws `DoesNotExistException` — the same as a pin that doesn't exist at all. Return 404 in both cases. Never confirm to a user whether a resource exists if they don't own it.

## Exercise: Verify user isolation

**1. Create pins as two users**

Log in as `bob` and create two or three pins via the Pinboard UI. Then log out and log in as `alice` and create a couple of pins there too.

**2. Verify list isolation**

Switch between `bob` and `alice` and confirm each user only sees their own pins in the UI. M4 confirmed this at the API level — this is a quick sanity check that the Vue frontend is correctly wired to the scoped endpoint.

**3. The ownership gotcha — test `getPin`**

Now for something more interesting. Find the ID of one of bob's pins directly from the database:

```bash
./scripts/mysql.sh -- -e "SELECT id, user_id, url FROM oc_pinboard_pins"
```

`occ` has no generic query command — `scripts/mysql.sh` (from the `nextcloud-docker-dev` toolkit) drops you into the MySQL client against the `nextcloud` database instead; `-e` runs a single statement and exits.

Pick one of bob's pin IDs and try to fetch it as alice:

```bash
curl -u alice:alice http://nextcloud.local/index.php/apps/pinboard/pins/<bob_pin_id>
```

You should get `404 Not found` — not bob's pin data, and crucially not a `403 Forbidden` either. The server doesn't confirm the pin exists at all. This is the `DoesNotExistException` behaviour from M4: a pin that exists but belongs to a different user throws the same exception as a pin that doesn't exist. The 404 is intentional — revealing that a resource *exists* to someone who can't access it is itself an information leak.

**4. Verify `deletePin` enforces ownership**

Try to delete one of bob's pins as alice:

```bash
curl -u alice:alice \
  -X DELETE \
  http://nextcloud.local/index.php/apps/pinboard/pins/<bob_pin_id>
```

You should again get `404 Not found`. Then confirm bob's pin still exists by logging back in as bob and checking the UI — the pin should be untouched.

## Common problems

**The `$userId` parameter injection fails with a "could not be resolved" error**  
The parameter must be named exactly `$userId`. Check for typos — `$currentUserId` or `$user_id` won't be resolved by the container.

**`$userId` is null in a `#[NoAdminRequired]` controller**  
This shouldn't happen in a real request. Check that `#[NoAdminRequired]` is on the method, not missing or misspelled.

**`DoesNotExistException` is uncaught and returns a 500**  
Wrap every `findById` call in a try/catch. An uncaught exception results in a 500 error rather than the 404 the client expects.
