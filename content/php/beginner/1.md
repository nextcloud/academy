## Path A: Docker-dev (recommended)

> **Haven't set up your environment yet?** Use the **Setting Up Your Development Environment** module — find it in the Standalone section on the course home screen, or in the "Before you start" section at the top of the course index. It covers Docker Desktop installation, cloning nextcloud-docker-dev, and getting Nextcloud running at `http://nextcloud.local`. Come back here once you can log in as `admin`.

The Docker-dev environment gives you a full local clone of the Nextcloud server source, a running Nextcloud instance (actually several), and a scripts directory with wrappers for common tasks. Here is what the setup does and why each part matters:

**`bootstrap.sh`** clones `nextcloud/server` into `workspace/server/` and installs its dependencies. Your app will live at `workspace/server/apps-extra/pinboard/`. Because this is a real git clone — not a build artifact — you can read the Nextcloud source code at any time, set breakpoints in it, and understand exactly what your app is calling into.

**`docker compose up -d`** starts the containers. The main one you'll interact with is called `nextcloud`. A second instance called `nextcloud2` is available for federation work later.

**`./scripts/occ.sh`** is the wrapper for Nextcloud's command-line tool. You will use this constantly. Its signature is:

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh <instance> -- <occ command>
# e.g.
./scripts/occ.sh nextcloud -- app:list
./scripts/occ.sh nextcloud -- config:system:get version
```

> **Working directory for all Docker-dev commands:** Unless stated otherwise, every `./scripts/occ.sh`, `docker compose`, and `mkdir workspace/...` command in this course must be run from the `nextcloud-docker-dev/` directory — the root of the repository you cloned during setup. A quick way to confirm you're in the right place: `ls scripts/occ.sh` should return the file, not an error.

Your Nextcloud instance runs at **http://nextcloud.local** (the bootstrap script adds a hosts entry). Admin credentials are `admin` / `admin`.

The environment also pre-creates several regular test users — no admin privileges, realistic for testing how your app behaves for normal users:

| Username | Password | Notes |
|---|---|---|
| `alice` | `alice` | Use as your primary test user throughout the course |
| `bob` | `bob` | Use as a second user for sharing and collaboration exercises |
| `jane` | `jane` | Use as a third user for group/multi-user scenarios |

The full user list is documented at [nextcloud.github.io/nextcloud-docker-dev](https://nextcloud.github.io/nextcloud-docker-dev). For now, alice and bob are the two you'll reach for most often — from Intermediate Module 2 onwards, sharing a pin from alice to bob will be the standard exercise pattern.

> **Why this matters for your app:** When you write `$this->userSession->getUser()` in your controller, the returned user depends entirely on who is logged in. Logging in as alice in your normal browser and as bob in a private/incognito window (or a different browser entirely) is the fastest way to verify that your app correctly scopes data per user — something you'll do constantly from Module 6 onwards. Two windows in the same browser share the session cookie, so they'd both show the same user.

## What the development environment gives you

Regardless of which path you chose, you now have:

**Debug mode** — needs to be enabled manually (covered in the exercise below). Once on, it means:
- PHP errors are displayed rather than swallowed
- Nextcloud's own debug output is verbose
- Additional browser console output is enabled for Nextcloud core

> **JavaScript source maps:** Readable JS in browser devtools is controlled by how your app's frontend is *built*, not by the server debug flag. When you reach Module 5 you'll run `npm run dev` or `npm run watch` in your app directory — those commands produce unminified output with source maps. The production `npm run build` strips them.

**Log tailing** — Nextcloud writes structured JSON logs to a file on disk. Because the log is written inside the Docker container, you need to tail it from inside the container for reliable real-time output — `tail -f` on the host may not receive inotify events correctly across the Docker filesystem layer. The command pipes the output through `jq`, a command-line JSON processor that pretty-prints each log entry so it's readable rather than a wall of minified JSON:

```bash
docker compose exec nextcloud bash -c \
  "tail -f /var/www/html/data/nextcloud.log | jq ."
```

`docker compose logs -f nextcloud` also exists but shows container-level output (PHP-FPM, nginx startup/crash messages) — useful for diagnosing why the container won't start, but not where your app's `$this->logger->info()` calls end up. The exec approach above is what you'll actually reach for day-to-day.

> **Silent logs:** Docker-dev ships with `loglevel 2` (warnings only) by default. Until you set it to `0` in the exercise below, your app's debug and info log calls will be silently swallowed — including errors in broken code that isn't throwing exceptions. This is the most common reason logs appear empty.

**Xdebug** — the PHP debugger is pre-configured in Docker-dev. If you use VS Code, the `launch.json` for step debugging is included. This is optional for Beginner work but worth knowing it's there.

## Why Nextcloud's dev environment is different from a typical PHP app

If you've developed plain PHP applications before, one thing will feel different immediately: **you don't run your code in isolation**. Your app is a guest inside a running Nextcloud process. This has a few practical consequences:

- You can't `php -S` your app or run it standalone. It only exists when Nextcloud loads it.
- A PHP syntax error in your app will show as a generic Nextcloud error unless debug mode is on.
- Clearing caches sometimes requires an `occ` command, not just a page refresh.
- The `workspace/server/` directory is the Nextcloud source — browsing it when you're confused about how something works is always a good idea.

This tight integration is also what makes Nextcloud app development powerful: your app has access to the full Nextcloud service layer the moment it's loaded. You don't wire up a database, authentication, or a filesystem — they're already there.

## Exercise: Verify your environment

Complete these steps before moving to Module 2. They confirm everything is working and introduce the tools you'll use throughout the course.

**1. Check Nextcloud is running and healthy**

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- status
```

Expected output includes `installed: true` and `version: 34.x.x`. If the version doesn't match, here's how to identify and fix it:

**Version shows `35.0.0-dev.x` or any `-dev` suffix**
You're on the `master` branch. Bootstrap defaulted to master because no branch was specified. Because Nextcloud doesn't support downgrading a database schema, you need to tear down the volumes and start fresh with the correct branch:
```bash
# Run from: ~/nextcloud-docker-dev/
docker compose down -v
git -C workspace/server checkout stable34
git -C workspace/server submodule update --init
docker compose up -d nextcloud
```
> **Note:** `docker compose down -v` destroys all data in the Docker volumes — the database, uploaded files, and any configuration you've done through the UI. That's fine at this stage since nothing is irreplaceable yet, but keep it in mind for later: once you're mid-course with test data you care about, note down any manual configuration before running this.

Wait ~60 seconds for the fresh install to complete, then re-run the status check.

**Version shows `33.x.x` or `32.x.x`**
Same situation — an older schema in the volumes means you can't simply upgrade to `stable34` in place. Tear down and rebuild the same way as above, substituting your current branch name. The same data-loss caveat applies.

**Version shows `34.x.x` but `installed: false`**
The server code is correct but the installation step didn't complete. Usually means the database container wasn't ready when Nextcloud first started. Fix:
```bash
# Run from: ~/nextcloud-docker-dev/
docker compose restart nextcloud
# Wait 30 seconds, then re-run the status check
./scripts/occ.sh nextcloud -- status
```
If it's still not installed after a restart, check the container logs for database connection errors: `docker compose logs nextcloud`.

**`occ` returns an error rather than output**
The containers may still be initialising — wait 30–60 seconds after `docker compose up` before running occ commands. If the error persists, `docker compose ps` will show which containers are unhealthy.

**2. Confirm you can enable and disable an app**

```bash
# Run from: ~/nextcloud-docker-dev/

# List all available apps
./scripts/occ.sh nextcloud -- app:list

# Enable the Activity app if it isn't already
./scripts/occ.sh nextcloud -- app:enable activity

# Confirm it's listed as enabled
./scripts/occ.sh nextcloud -- app:list --enabled
```

**3. Enable debug mode and verbose logging**

Docker-dev ships with `loglevel 2` (warnings only) and debug mode off. You need to set both for a useful development experience. The right way to do this in docker-dev is via `data/shared/config.php` — a file that gets included after the default config and survives container rebuilds:

```bash
# Run from: ~/nextcloud-docker-dev/
cat > data/shared/config.php << 'EOF'
<?php
$CONFIG = [
    'debug' => true,
    'loglevel' => 0,
];
EOF
```

Then restart the container to pick up the change:

```bash
docker compose restart nextcloud
```

Verify both settings took effect:

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- config:system:get debug
# Expected: true

./scripts/occ.sh nextcloud -- config:system:get loglevel
# Expected: 0
```

> **`loglevel 0` means all log output including debug** — your log file will be noisy during development. That's intentional. You'd set it back to `2` in production. The `data/shared/config.php` approach means you only need to do this once — it persists across `docker compose down` / `up` cycles.

**4. Trigger a log entry and find it**

In a separate terminal, start tailing the log from inside the container:

```bash
docker compose exec nextcloud bash -c \
  "tail -f /var/www/html/data/nextcloud.log | jq ."
```

Now open your Nextcloud instance in a browser (http://nextcloud.local or the Codespaces forwarded URL) and log in as `admin`. You should see log entries appear in real time. Find one with `"app":"core"` and note the structure — every log entry has `level`, `time`, `app`, `message`, and optionally `data`. Your app will write entries in exactly this format in later modules.

## Common problems

**`nextcloud.local` doesn't resolve**
`bootstrap.sh` adds an entry to `/etc/hosts`. If it didn't work, add both IPv4 and IPv6 entries manually:
```
127.0.0.1 nextcloud.local
::1 nextcloud.local
```
On Windows with WSL2, these need to go in the Windows hosts file at `C:\Windows\System32\drivers\etc\hosts`.

**`./scripts/occ.sh` returns "container not running"**  
The containers aren't up. Run `docker compose up -d` from the `nextcloud-docker-dev` directory and wait ~30 seconds for Nextcloud to initialise.

**Port conflict on 80/443**
Another service (nginx, Apache, another Docker project) is using port 80. You have two options:

*Option 1 — Stop the conflicting service:*
```bash
# nginx
sudo systemctl stop nginx

# Apache
sudo systemctl stop apache2   # Debian/Ubuntu
sudo systemctl stop httpd     # RHEL/Fedora

# Another Docker Compose project
docker compose -f /path/to/other/docker-compose.yml down
```

*Option 2 — Remap the port in docker-compose.yml:*
Open `docker-compose.yml` in the `nextcloud-docker-dev` directory and find the `nextcloud` service's port mapping. Change the host-side port (the number before the colon):
```yaml
# Change this:
ports:
  - "80:80"
# To something like:
ports:
  - "8080:80"
```
Then access your instance at `http://nextcloud.local:8080` instead of `http://nextcloud.local`.

Either way, port mappings can't be changed on a running container — you need to stop and recreate it. Unlike the version mismatch fix, you don't need `-v` here since the volumes (your database and files) are unaffected:
```bash
# Run from: ~/nextcloud-docker-dev/
docker compose down
docker compose up -d nextcloud
```

## NC34 notes

If you're coming from tutorials written for NC32 or NC33, the development environment itself is unchanged. The differences that affect your app code come in later modules. One thing to be aware of now: the NC34 upgrade removed several globally available JavaScript libraries (jQuery, OC.Apps, OC.Notifications). If you look at older app code in `workspace/server/apps/` and see these being used, know that they no longer work in NC34 — you'll learn the modern replacements in Module 5.
