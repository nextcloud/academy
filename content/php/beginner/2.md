# Module 2: App Anatomy

**Track:** PHP App Track — Beginner  
**Estimated time:** 40 minutes  
**Git tag start:** `php/beginner/m1-complete`  
**Git tag end:** `php/beginner/m2-complete`  
**You'll have when done:** A discoverable, installable Pinboard app — no functionality yet, but Nextcloud knows it exists, can enable and disable it, and shows it in the navigation bar.

---

## Why this matters

Before writing a single line of business logic, you need Nextcloud to recognise your code as an app. This isn't a formality — the structure you set up here is the contract between your code and the Nextcloud platform. Get the directory layout wrong and your classes won't autoload. Get the manifest wrong and the app store will reject your submission. Get the bootstrap class wrong and your services won't register.

This module explains *why* each piece exists, not just what to create. By the end you'll be able to look at any Nextcloud app on GitHub and immediately understand its skeleton.

---

## The Nextcloud app model

A Nextcloud app is not a standalone PHP application. It's a **plugin loaded into a running Nextcloud platform**. This has one important consequence for how you think about structure:

Nextcloud discovers your app by its directory name, loads a manifest to learn about it, then — when a request comes in that involves your app — instantiates your `Application` class, calls its `register()` method to wire up services, and eventually calls your controller. Every request goes through this sequence. Your app never runs on its own.

This also means the directory name *is* the app ID. The directory `workspace/server/apps-extra/pinboard/` makes the app ID `pinboard`. It must match exactly throughout: in the manifest, in PHP namespaces, in route names, in database table prefixes. Inconsistency here produces errors that are hard to trace.


This gives you your own copy of the repo with the full git history and all module tags, so you can use the recovery links throughout the course and push your own work as you go. The scaffold already includes a `.gitignore` covering `node_modules/` and other files that shouldn't be committed.

## Concepts

### The manifest — `appinfo/info.xml`

The manifest is the first thing Nextcloud and the app store read. It tells the platform who you are, what version you are, and what Nextcloud versions you support. It's validated against an [XML schema](https://apps.nextcloud.com/schema/apps/info.xsd) — a malformed manifest will silently prevent your app from appearing.

Open `appinfo/info.xml` in your scaffold and replace the stub with:

```xml
<?xml version="1.0"?>
<!--
  - SPDX-FileCopyrightText: 2025 Your Name
  - SPDX-License-Identifier: AGPL-3.0-or-later
-->
<info xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xsi:noNamespaceSchemaLocation="https://apps.nextcloud.com/schema/apps/info.xsd">
    <id>pinboard</id>
    <name>Pinboard</name>
    <summary>Save, tag and share links</summary>
    <description><![CDATA[A simple app for saving and organising links, built as part of the Nextcloud Developer Course.]]></description>
    <version>0.1.0</version>
    <licence>agpl</licence>
    <author>Your Name</author>
    <category>tools</category>
    <dependencies>
        <php min-version="8.3" />
        <nextcloud min-version="34" max-version="34" />
    </dependencies>
    <navigations>
        <navigation>
            <id>pinboard</id>
            <name>Pinboard</name>
            <route>pinboard.page.index</route>
            <icon>app.svg</icon>
            <order>10</order>
        </navigation>
    </navigations>
</info>
```

A few things worth understanding here:

**`<id>`** must exactly match your app directory name — `pinboard`. This is the app's permanent identifier. Once you publish an app, you can never change this.

**`<version>`** follows semantic versioning. Nextcloud uses this to determine whether to run your database migrations when a user updates. Incrementing it without a migration is fine; shipping a migration without incrementing it means it will never run.

**`<licence>`** is `agpl` (not `AGPL-3.0-or-later` — the schema has its own values). Apps in the official store must use a licence compatible with AGPL-3.0-or-later — this includes MIT, Apache-2.0, and other permissive licences, since they can be combined with AGPL code. Proprietary or copyleft licences incompatible with AGPL (such as GPL-2.0-only) are not allowed. Most Nextcloud apps simply use AGPL-3.0-or-later itself, which is what we'll use for Pinboard.

The SPDX comment at the top of the file (`SPDX-FileCopyrightText` / `SPDX-License-Identifier`) is a separate concern from the `<licence>` tag. SPDX is a machine-readable standard for declaring copyright and licence information — tools, CI pipelines, and legal scanners can parse it automatically without reading prose. Every file in a properly licensed project should carry its own SPDX header, not just the manifest. You'll see these headers in every current Nextcloud app and in every PHP file we write in this course:

```php
/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */
```

The `FileCopyrightText` line records who holds copyright and when. The `License-Identifier` uses a standardised identifier from the [SPDX licence list](https://spdx.org/licenses/) — `AGPL-3.0-or-later` means the GNU Affero General Public License version 3, with the option to use any later version.

> **SPDX and your files:** Every PHP file, template, and JavaScript file you create in this course should carry its own SPDX header. It takes two lines and saves significant effort if you ever need to audit or relicense your project later.

**`<namespace>`** is absent here because our app ID (`pinboard`) and PHP namespace (`OCA\Pinboard`) match. Some apps use a different directory name from their namespace — Talk, for example, lives in `apps/spreed/` but uses `OCA\Talk\` — and those apps need `<namespace>Talk</namespace>` to tell the autoloader where to look. If yours match, omit it.

**`<dependencies>`** is where you declare the PHP version and Nextcloud version range your app supports.

For PHP, NC34 supports 8.2 (deprecated), 8.3, 8.4, and 8.5 (recommended). We set `min-version="8.3"` to avoid the deprecated 8.2 — there's no practical reason to support it for a new app. For future reference, the supported PHP versions for any Nextcloud release are listed on the [Nextcloud system requirements page](https://docs.nextcloud.com/server/latest/admin_manual/installation/system_requirements.html).

For the Nextcloud version range, setting both `min-version="34"` and `max-version="34"` is intentional for now — it prevents your app from being enabled on instances older than NC34 where APIs may differ, and from being silently enabled on an NC35 instance where you haven't tested it yet. You'll update this as you verify compatibility.

**`<navigation>`** is what puts your app in the top navigation bar. The `<id>` must match your app ID. The `<icon>` points to a file in your `img/` directory — Nextcloud uses `img/app.svg` and `img/app-dark.svg` for light and dark mode. The `<route>` value `pinboard.page.index` is a route name — we'll define what this means in a moment. This is the simpler of two approaches — the other is registering programmatically via `INavigationManager` in your `Application.php`, which some complex apps (like Talk) use when they need more control. For Pinboard, the `info.xml` approach is correct.

> **`max-version` and the app store:** When you eventually publish, keep `max-version` up to date. Each time a new Nextcloud version ships, apps whose `max-version` doesn't include it will show as incompatible in the store. The usual workflow is to test your app against the new version, then bump `max-version` as part of each Nextcloud release cycle.

### The router — `appinfo/routes.php`

Routes connect URLs to controller methods. Open `appinfo/routes.php` and add:

```php
<?php
/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */

declare(strict_types=1);

return [
    'routes' => [
        ['name' => 'page#index', 'url' => '/', 'verb' => 'GET'],
    ],
];
```

The `name` field encodes the controller and method in a single string. `page#index` means: look for a class called `PageController` in your app's `Controller/` directory, and call its `index()` method. Nextcloud derives the full class name from your app ID and namespace automatically — `OCA\Pinboard\Controller\PageController`.

The `#` separator is not arbitrary punctuation — it's the Nextcloud convention for `controller#method`. The part before `#` maps to a controller class (with `Controller` appended), the part after maps to a method.

The full URL this produces is `/index.php/apps/pinboard/` — your app's root. This is also what the `<route>pinboard.page.index</route>` in `info.xml` references: `appid.controllername.methodname`, all dots.

You don't need to create the `PageController` yet — that's Module 3. The route can exist before the controller; Nextcloud will just return a 404 if someone hits the URL before the controller is in place.

### The bootstrap class — `lib/AppInfo/Application.php`

The `Application` class is what Nextcloud instantiates when it loads your app. It's where you register services with the dependency injection container, connect event listeners, and declare capabilities. Open `lib/AppInfo/Application.php` and fill it in:

```php
<?php
/**
 * SPDX-FileCopyrightText: 2025 Your Name
 * SPDX-License-Identifier: AGPL-3.0-or-later
 */

declare(strict_types=1);

namespace OCA\Pinboard\AppInfo;

use OCP\AppFramework\App;
use OCP\AppFramework\Bootstrap\IBootContext;
use OCP\AppFramework\Bootstrap\IBootstrap;
use OCP\AppFramework\Bootstrap\IRegistrationContext;

class Application extends App implements IBootstrap {

    public const APP_ID = 'pinboard';

    public function __construct() {
        parent::__construct(self::APP_ID);
    }

    public function register(IRegistrationContext $context): void {
        // Services, event listeners, and capabilities are registered here.
        // This runs before any services are instantiated.
    }

    public function boot(IBootContext $context): void {
        // Code that runs once all apps have registered.
        // Keep this as empty as possible — heavy boot() logic slows every request.
    }
}
```

Three things to understand here:

**Why `IBootstrap`?** Your class *must* extend `OCP\AppFramework\App`. Implementing `IBootstrap` is optional but strongly recommended for any app that registers services. Without it, Nextcloud only calls your constructor, which limits what you can safely do. With `IBootstrap`, Nextcloud calls `register()` on all apps first, *then* `boot()` on all apps — this interleaving ensures that when your `boot()` runs, every other app's services are already registered and available.

**`APP_ID` constant** — defining the app ID as a constant prevents the string `'pinboard'` from being scattered through your codebase. You'll reference `Application::APP_ID` in controllers, mappers, and settings classes throughout the course.

**`register()` vs `boot()`** — `register()` is for declaring what exists (service bindings, event listener registrations, capability declarations). `boot()` is for code that needs to *run*. For now both are empty — you'll add to `register()` from Module 5 onwards as you add services and listeners.

> **OCP vs OC:** Notice all the `use` statements import from `OCP\` — the public API namespace. You'll see `OC\` in the Nextcloud source code itself, but that's internal. Your app must only ever import from `OCP\`. The distinction matters: `OCP\` classes are stable across versions; `OC\` classes can change or disappear in any release. This is explored in depth in Intermediate Module 1.

### Why is the directory structure the way it is?

Nextcloud has a built-in classloader that automatically maps the `OCA\Pinboard\` namespace to `apps-extra/pinboard/lib/` (or `apps/pinboard/lib/` for Nextcloud's own bundled apps). You don't need to register your classes anywhere or set up a `composer.json` — for your own app classes, the convention of matching namespace to file path is enough. This is why:
- `lib/AppInfo/Application.php` → `OCA\Pinboard\AppInfo\Application`
- `lib/Controller/PageController.php` → `OCA\Pinboard\Controller\PageController`
- `lib/Db/PinMapper.php` → `OCA\Pinboard\Db\PinMapper`

This built-in autoloading only covers your app's own classes under `lib/`. When you start using third-party Composer packages (covered in Intermediate), you'll add a `composer.json` and explicitly include the Composer autoloader in `Application::register()` with `include_once __DIR__ . '/../../vendor/autoload.php'`.

## Exercise: Make Nextcloud discover the Pinboard app

**1. Enable the app**

With your manifest in place, Nextcloud can now discover and enable Pinboard:

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- app:enable pinboard
```

Expected output: `pinboard enabled`

If you get `Could not enable app pinboard` — check your `info.xml` for XML errors (an unclosed tag, a wrong licence value, a mismatched `<id>` and directory name). The log will have details:

```bash
# Run from: ~/nextcloud-docker-dev/
tail -f workspace/server/data/nextcloud.log | python3 -m json.tool
```

**2. Confirm it appears in the app list**

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- app:list --enabled | grep pinboard
```

You should see `pinboard` listed with its version.

**3. Check the navigation bar**

Open `http://nextcloud.local` in your browser and log in as `admin`. You should see **Pinboard** in the top navigation bar. Clicking it will give you a 404 for now — that's expected, since the `PageController` doesn't exist yet. The important thing is that the link is there and the URL is `/index.php/apps/pinboard/`.

**4. Check that your namespace is correct**

Open `lib/AppInfo/Application.php` and confirm:

- The `namespace` declaration is `OCA\Pinboard\AppInfo;`
- The class name is `Application`
- The file path is `workspace/server/apps-extra/pinboard/lib/AppInfo/Application.php`

If any of these three don't align, the autoloader will fail silently — Nextcloud will act as if your `Application` class doesn't exist.

**5. Disable and re-enable**

```bash
# Run from: ~/nextcloud-docker-dev/
./scripts/occ.sh nextcloud -- app:disable pinboard
./scripts/occ.sh nextcloud -- app:enable pinboard
```

This confirms the manifest is valid enough to survive a disable/enable cycle, which is how Nextcloud processes updates in production.

## Common problems

**`app:enable` fails with no useful message**
Enable debug mode and check the log — it will usually say something about malformed XML or a missing required field. The most common culprits: `<id>` doesn't match directory name, `<licence>` uses the wrong format (`AGPL-3.0` instead of `agpl`), or the XML schema URL in the opening tag is wrong.

**Pinboard doesn't appear in the navigation bar after enabling**  
Two common causes:

- **Wrong XML structure** — `<navigation>` must be wrapped in a `<navigations>` parent and placed after `<dependencies>`. The schema requires `<navigations><navigation>...</navigation></navigations>`, not a bare `<navigation>` directly inside `<info>`. Also check that the elements appear in the correct order — the schema enforces strict sequencing.
- **Stale JS cache** — the navigation bar is rendered client-side. Try a hard refresh (`Ctrl+Shift+R` on Windows/Linux, `Cmd+Shift+R` on Mac). If that doesn't help, run `app:disable` then `app:enable` to force a re-read of the manifest.

**App appears in the navigation bar but shows a broken or missing icon**  
Nextcloud looks for `img/app.svg` in your app directory. Without it the app shows a generic fallback icon. The scaffold includes a placeholder — if you've removed it or it's missing, create `img/app.svg` with any valid SVG. The icon must use `fill="#fff"` (white) — Nextcloud loads it as an `<img>` so CSS inheritance doesn't apply, and the `--primary-invert-if-bright` filter handles flipping it dark when needed.

**`Could not enable app: version x.x.x is not compatible`**
Your `<nextcloud min-version>` or `<nextcloud max-version>` doesn't include version 34. Check `./scripts/occ.sh nextcloud -- status` for the exact version, and adjust the manifest to match.

**Clicking the nav entry gives a 500 error rather than a 404**
This means the `Application` class was found but threw an error during instantiation. Check the log for a PHP fatal — usually a wrong namespace, a missing `use` statement, or a syntax error in `Application.php`.

It's a useful reference. We're not using it here because understanding each file's purpose *is the point of this module* — a generated app hands you 300 lines of boilerplate before you know what any of it does. ## NC34 notes

The `IBootstrap` interface (`register()` / `boot()`) has been the standard since NC20. If you encounter older tutorials using `appinfo/app.php` — a file that ran arbitrary code on every request — that pattern is deprecated and gone in NC34. The `Application` class with `IBootstrap` is the only supported approach.
