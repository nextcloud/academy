## Getting your ExApp into the world — why packaging matters

ExApp packaging is significantly different from PHP app packaging. A PHP app is a zip of source files — Nextcloud unpacks it and loads the PHP directly. An ExApp is a **Docker image** — Nextcloud tells AppAPI to pull and run a container. This means:

- The app store doesn't host your code — it hosts a reference to your Docker image on a registry (GitHub Container Registry, Docker Hub, etc.)
- Every release requires building and pushing a new Docker image, not just creating a tarball
- Your image must support both `linux/amd64` and `linux/arm64` to work on all Nextcloud server hardware
- `appinfo/info.xml` must include the `<docker-install>` block pointing to your image

The upside: updates are atomic, rollback is straightforward (just re-register the previous image tag), and your runtime environment is perfectly reproducible.

## Semantic versioning and the version bump

The same four-file sync principle as the PHP track, adapted for Python:

- **`appinfo/info.xml`** — `<version>` tag
- **`requirements.txt`** — doesn't contain a version, but should be kept current
- **`CHANGELOG.md`** — human-readable release notes
- **`pyproject.toml`** or **`setup.cfg`** if you have one — optional for ExApps, but good practice

For Pinboard, bump `appinfo/info.xml` from `0.1.0` to `1.0.0` and update `CHANGELOG.md`:

```markdown
# Changelog

## 1.0.0 - 2025-06-01

### Added
- Pin URLs with optional titles
- User-scoped pin storage — each user sees only their own pins
- Vue 3 frontend with add, view, and delete pin functionality
- SQLite database with SQLAlchemy ORM
```

## The info.xml store fields

Update `appinfo/info.xml` with the complete set of store fields before packaging:

```xml
<?xml version="1.0"?>
<!--
  SPDX-FileCopyrightText: 2025 Your Name
  SPDX-License-Identifier: AGPL-3.0-or-later
-->
<info xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xsi:noNamespaceSchemaLocation="https://apps.nextcloud.com/schema/apps/info.xsd">
  <id>pinboard_python</id>
  <name>Pinboard</name>
  <summary>Save and organise URLs in your Nextcloud</summary>
  <description><![CDATA[
    Pinboard lets you save, tag and organise URLs directly in your Nextcloud interface.
    Each user's pins are private to them. Built with Python and FastAPI via AppAPI.
  ]]></description>
  <version>1.0.0</version>
  <licence>agpl</licence>
  <author mail="you@example.com" homepage="https://yoursite.com">Your Name</author>
  <category>organization</category>
  <bugs>https://github.com/YOUR_USERNAME/pinboard-python/issues</bugs>
  <repository>https://github.com/YOUR_USERNAME/pinboard-python</repository>
  <dependencies>
    <nextcloud min-version="34" max-version="34"/>
  </dependencies>
  <external-app>
    <docker-install>
      <registry>ghcr.io</registry>
      <image>YOUR_GITHUB_USERNAME/pinboard-python</image>
      <image-tag>1.0.0</image-tag>
    </docker-install>
    <routes>
      <route>
        <url>.*</url>
        <verb>GET,POST,PUT,DELETE</verb>
        <access_level>USER</access_level>
        <headers_to_exclude>[]</headers_to_exclude>
        <bruteforce_protection>[401, 500]</bruteforce_protection>
      </route>
    </routes>
  </external-app>
</info>
```

**`<image-tag>`** — use the exact version tag, not `latest`. Using `latest` means administrators can't pin to a specific version and rollback becomes impossible. Tag each release with the version number.

## The Dockerfile

Create `Dockerfile` in the project root. This defines what goes into your Docker image:

```dockerfile
# SPDX-FileCopyrightText: 2025 Your Name
# SPDX-License-Identifier: AGPL-3.0-or-later

#############################
# Stage 1: Builder
#############################
FROM python:3.12-slim-bookworm AS builder

# Install build dependencies
RUN apt-get update && apt-get install -y curl && \
    apt-get clean && rm -rf /var/lib/apt/lists/*

# Install Python dependencies
COPY requirements.txt /
RUN --mount=type=cache,target=/root/.cache/pip \
    python3 -m pip install --root-user-action=ignore -r requirements.txt && \
    rm requirements.txt

# Download FRP client for AppAPI HaRP proxy support
RUN set -ex; \
    ARCH=$(uname -m); \
    if [ "$ARCH" = "aarch64" ]; then \
      FRP_URL="https://raw.githubusercontent.com/nextcloud/HaRP/main/exapps_dev/frp_0.61.1_linux_arm64.tar.gz"; \
    else \
      FRP_URL="https://raw.githubusercontent.com/nextcloud/HaRP/main/exapps_dev/frp_0.61.1_linux_amd64.tar.gz"; \
    fi; \
    curl -L "$FRP_URL" -o /tmp/frp.tar.gz; \
    tar -C /tmp -xzf /tmp/frp.tar.gz; \
    mv /tmp/frp_0.61.1_linux_* /tmp/frp; \
    cp /tmp/frp/frpc /usr/local/bin/frpc; \
    chmod +x /usr/local/bin/frpc; \
    rm -rf /tmp/frp /tmp/frp.tar.gz

#############################
# Stage 2: Runtime
#############################
FROM python:3.12-slim-bookworm

# Copy installed packages and FRP from builder
COPY --from=builder /usr/local/ /usr/local/

# Add ExApp static and backend files
ADD /ex_app/css[s] /ex_app/css
ADD /ex_app/im[g]  /ex_app/img
ADD /ex_app/j[s]   /ex_app/js
ADD /ex_app/l10[n] /ex_app/l10n
ADD /ex_app/li[b]  /ex_app/lib

# Copy startup and health check scripts
COPY --chmod=775 healthcheck.sh /
COPY --chmod=775 start.sh /

WORKDIR /ex_app/lib
ENTRYPOINT ["/start.sh", "python3", "main.py"]
HEALTHCHECK --interval=2s --timeout=2s --retries=300 CMD /healthcheck.sh
```

**Multi-stage build** — the builder stage installs dependencies and downloads the FRP client. The runtime stage copies only what's needed, keeping the image small.

**FRP client** — required for AppAPI's HaRP (High-performance AppAPI Reverse Proxy) deploy daemon. Without it, your image won't work with production HaRP deployments. The `manual_install` daemon doesn't need it, but include it for production compatibility.

**`ADD /ex_app/j[s]`** — the bracket glob is intentional. If the directory doesn't exist, `ADD` with a glob fails silently rather than erroring. This lets you ship images without a frontend if needed.

Create `healthcheck.sh`:

```bash
#!/bin/bash
# SPDX-FileCopyrightText: 2025 Your Name
# SPDX-License-Identifier: AGPL-3.0-or-later
curl -sf http://localhost:${APP_PORT}/heartbeat > /dev/null
```

Create `start.sh`:

```bash
#!/bin/bash
# SPDX-FileCopyrightText: 2025 Your Name
# SPDX-License-Identifier: AGPL-3.0-or-later
set -e
APP_HOST=0.0.0.0 exec "$@"
```

## Build and push the Docker image

You'll need Docker's buildx plugin for multi-platform builds:

```bash
# Run from: ~/pinboard-python/
# One-time setup: create a multi-platform builder
docker buildx create --name pinboard-builder --driver docker-container \
  --platform linux/amd64,linux/arm64/v8 --use

# Log in to GitHub Container Registry
docker login ghcr.io

# Build and push (replace YOUR_GITHUB_USERNAME)
docker buildx build --push \
  --platform linux/arm64/v8,linux/amd64 \
  --tag ghcr.io/YOUR_GITHUB_USERNAME/pinboard-python:1.0.0 \
  --tag ghcr.io/YOUR_GITHUB_USERNAME/pinboard-python:latest \
  .
```

> **Always push a versioned tag alongside `latest`.** The `latest` tag is convenient for testing but administrators need versioned tags to pin to a known good release and roll back if needed.

> **Building for both `linux/amd64` and `linux/arm64/v8`** ensures your image works on both x86 servers (most cloud VMs) and ARM servers (Apple Silicon, Raspberry Pi, AWS Graviton). Omitting ARM support means your app won't work on a significant portion of Nextcloud installations.

Add `make build-push` to your Makefile:

```makefile
.PHONY: build-push
build-push:
	npm run build
	docker login ghcr.io
	docker buildx build --push \
		--platform linux/arm64/v8,linux/amd64 \
		--tag ghcr.io/$(GITHUB_USERNAME)/$(APP_ID):$(APP_VERSION) \
		--tag ghcr.io/$(GITHUB_USERNAME)/$(APP_ID):latest \
		.
```

And add `GITHUB_USERNAME` to the Makefile variables:

```makefile
GITHUB_USERNAME := YOUR_GITHUB_USERNAME
```

## App store submission

The submission process is the same as for PHP apps, but the app store downloads your Docker image rather than a tarball.

**1. Register your app** — go to [apps.nextcloud.com/developer/apps/new](https://apps.nextcloud.com/developer/apps/new). You'll need a code-signing certificate — the same process as PHP M8: generate a CSR with `openssl req`, submit a PR to [app-certificate-requests](https://github.com/nextcloud/app-certificate-requests), and wait for your `.crt`.

**2. Upload a release** — go to [apps.nextcloud.com/developer/apps/releases/new](https://apps.nextcloud.com/developer/apps/releases/new). Provide your `appinfo/info.xml` URL (e.g. from your GitHub repository's raw URL) — the store reads the `<docker-install>` block to know which image to pull. Provide the release signature.

**3. Administrators install** — when an admin installs Pinboard from the app store, AppAPI pulls `ghcr.io/YOUR_USERNAME/pinboard-python:1.0.0`, starts a container, waits for `/heartbeat`, then calls `/enabled`. No manual registration needed.

## The release checklist

Before every release:

- ☐ Version bumped in `appinfo/info.xml`
- ☐ `CHANGELOG.md` updated
- ☐ `<image-tag>` in `info.xml` updated to match the new version
- ☐ Production frontend built: `npm run build`
- ☐ Docker image built and pushed with versioned tag
- ☐ Git tag created and pushed
- ☐ GitHub release created (optional but recommended — attach `appinfo/info.xml` as an asset for the store URL)
- ☐ App store release uploaded

## Common problems

**`docker buildx build` fails with "no such platform"**  
Your buildx instance doesn't support ARM. Run the `docker buildx create` command from above to create a `docker-container` driver instance that supports QEMU-based cross-compilation.

**Image pushed but app store can't pull it**  
The image may be private. Go to your GitHub package settings and set the visibility to public, or configure the registry credentials in AppAPI.

**`healthcheck.sh` fails inside the container**  
`curl` isn't installed. Add `RUN apt-get install -y curl` to the runtime stage (after the builder stage COPY).

**App installs from store but `/heartbeat` times out**  
Your `ENTRYPOINT` is wrong or `main.py` crashes on startup. Check the container logs: `docker logs <container_name>`.
