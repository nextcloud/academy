## How ExApps work — the microservice model

An ExApp is a **microservice**: a standalone HTTP server that Nextcloud communicates with over a network. Nextcloud doesn't load your Python code directly — it makes HTTP requests to your microservice, your microservice responds, and Nextcloud uses those responses.

This means:
- Your code runs in its own process, with its own memory, its own dependencies, its own runtime
- You can use any library — PyTorch, OpenCV, pandas, anything — without worrying about Nextcloud's PHP environment
- Nextcloud and your ExApp can run on different machines
- Your server must be running before Nextcloud can communicate with it

The microservice can be written in **any language** — Go, Rust, Node.js, Ruby, whatever your team knows or your use case demands. The only requirement is that it speaks HTTP and implements the AppAPI lifecycle endpoints. We're using Python here because `nc_py_api` gives you a fully-featured client library that handles authentication, lifecycle registration, and all the Nextcloud API calls out of the box — writing the same from scratch in another language is possible but significantly more work.

The tradeoff: there's more infrastructure. Nextcloud needs to know where your server is (the daemon), your server needs to authenticate requests from Nextcloud (AppAPIAuthMiddleware), and both sides need to follow a communication protocol (the lifecycle).

### The communication flow

Every request follows one of two directions:

**Nextcloud → ExApp:** AppAPI routes requests to your FastAPI server. This is how lifecycle events (enable, disable) and user actions (file menu clicks, UI interactions) reach your Python code. These requests are authenticated with a shared secret.

**ExApp → Nextcloud:** Your Python code calls Nextcloud's OCS APIs to register features, read files, send notifications, look up users. These calls go through `nc_py_api` and are authenticated using the `AUTHORIZATION-APP-API` header containing your app's credentials.

In the `manual_install` development setup you're using, the flow looks like this:

```
# Conceptual flow — not a command
User browser
     │
     ▼
Nextcloud (in Docker at nextcloud.local)
     │  AppAPI routes to ExApp
     ▼
http://host.docker.internal:23000   ← your FastAPI server (on host machine)
     │  nc_py_api calls back
     ▼
Nextcloud OCS APIs
```

## The directory structure

The standard ExApp directory layout follows a specific convention. Rather than creating each file by hand, fork the Pinboard ExApp scaffold repository on GitHub and clone it:

```bash
# Run from: ~/  (or wherever you keep projects)
git clone https://github.com/YOUR_USERNAME/pinboard-python
cd pinboard-python
```

The scaffold gives you this structure:

```text
# Structure of: ~/pinboard-python/
pinboard-python/
├── appinfo/
│   └── info.xml          ← ExApp manifest
├── ex_app/
│   ├── lib/
│   │   └── main.py       ← your Python server
│   ├── img/              ← app icons
│   ├── css/              ← stylesheets
│   └── js/               ← compiled frontend assets
├── l10n/                 ← translation files (empty for now)
├── Makefile              ← development commands
├── requirements.txt      ← Python dependencies
└── .gitignore
```

The `ex_app/lib/` path for Python code is the established ExApp convention. Static assets — icons, CSS, compiled JavaScript — go under `ex_app/img/`, `ex_app/css/`, and `ex_app/js/` respectively. `nc_py_api` automatically mounts these folders to FastAPI when your server starts, so Nextcloud can access them through AppAPI's proxy.

## The manifest — appinfo/info.xml

Every ExApp has an `appinfo/info.xml` that tells Nextcloud and the app store about it. It shares most fields with regular Nextcloud apps but adds an `<external-app>` block.

Create `appinfo/info.xml`:

```xml
<?xml version="1.0"?>
<!--
  SPDX-FileCopyrightText: 2025 Your Name
  SPDX-License-Identifier: AGPL-3.0-or-later
-->
<info xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      xsi:noNamespaceSchemaLocation="https://apps.nextcloud.com/schema/apps/info.xsd">
  <id>pinboard_python</id>
  <name>Pinboard</name>
  <summary>Save and organise URLs in your Nextcloud</summary>
  <description><![CDATA[
    Pinboard lets you save, tag and organise URLs directly in your Nextcloud interface.
    Built as part of the Nextcloud Developer Course — ExApp Python track.
  ]]></description>
  <version>0.1.0</version>
  <licence>agpl</licence>
  <author>Your Name</author>
  <category>organization</category>
  <dependencies>
    <nextcloud min-version="34" max-version="34"/>
  </dependencies>
  <external-app>
    <docker-install>
      <registry>ghcr.io</registry>
      <image>YOUR_GITHUB_USERNAME/pinboard-python</image>
      <image-tag>latest</image-tag>
    </docker-install>
    <routes>
      <route>
        <url>.*</url>
        <verb>GET,POST,PUT,DELETE</verb>
        <access_level>USER</access_level>
        <headers_to_exclude>[]</headers_to_exclude>
        <bruteforce_protection>[401, 500]</bruteforce_protection>
      </route>
    </routes>
  </external-app>
</info>
```

### Key differences from a regular app manifest

**`<id>`** — ExApp IDs conventionally use underscores rather than hyphens: `pinboard_python` not `pinboard-python`. This is because the ID is used as a Python package name in some contexts.

**`<external-app>`** — required for all ExApps. The `<docker-install>` block tells AppAPI where to find your Docker image for production deployment. For development with `manual_install` this block is present but not used — AppAPI only reads it when deploying via Docker daemon.

**No `<navigations>` yet** — navigation entries for ExApps are registered programmatically during `enabled_handler`, not declared in `info.xml`. You'll add this in B-04.

          **`<routes>`** — declares which URL patterns AppAPI is allowed to proxy to your ExApp. The wildcard `url>.*<` with `access_level>USER<` means any authenticated user can reach any endpoint on your server through the AppAPI proxy. Without this block, AppAPI will refuse to forward requests to your app and all endpoint calls will return 404.

**No PHP version requirement** — ExApps have no PHP dependency, so `<php min-version>` is absent.

> **A note on scopes:** Older ExApp manifests contain a `<scopes>` block inside `<external-app>`. This was deprecated in AppAPI 3.0 and removed in AppAPI 3.2. Do not add it. Scopes are now passed via the `--force-scopes` flag during registration.

## The lifecycle — what AppAPI expects from your server

When AppAPI registers or interacts with your ExApp, it calls specific HTTP endpoints on your server in a defined order. Understanding this sequence explains why the skeleton is structured the way it is.

### `/heartbeat` — are you alive?

`GET /heartbeat`

AppAPI polls this endpoint periodically to check your server is up. It expects HTTP 200. No authentication required — this is intentionally public so AppAPI can check liveness without credentials.

`nc_py_api` registers this endpoint automatically when you call `set_handlers()`. You never write it yourself.

### `/init` — do you need to set up? (optional)

`POST /init`

Called once after heartbeat succeeds, before `/enabled`. Intended for long-running initialisation — downloading models, migrating data, seeding a database. Your server reports progress back to Nextcloud during this phase.

If your app doesn't implement `/init`, AppAPI receives a 404 or 501 and skips straight to `/enabled`. Pinboard doesn't need init — `set_handlers()` handles the 404 response automatically.

### `/enabled` — register or unregister your features

`PUT /enabled?enabled=1` — enable  
`PUT /enabled?enabled=0` — disable

This is the most important lifecycle call. When enabled, your app should register everything it offers: navigation entries, file action menus, background jobs, OCC commands. When disabled, unregister all of them.

Your `enabled_handler` function is called by `set_handlers()` for both states. The `enabled` bool parameter tells you which direction.

**Critical constraint:** no user context is available during this call. `nc.user` is empty. Any nc_py_api call that requires a user (file operations, user preferences) will fail with an authentication error. Only system-level API calls work here.

**Return value matters:** return an empty string `""` on success. Return a non-empty string to signal failure — AppAPI will show it to the administrator and abort the enable process. This is your only way to communicate setup errors back to Nextcloud.

The full lifecycle in sequence:

```
AppAPI registers ExApp
        │
        ├─→ GET /heartbeat  (repeated until 200, timeout 10 min)
        │
        ├─→ POST /init      (optional — skip if 404/501)
        │
        └─→ PUT /enabled?enabled=1
                │
                enabled_handler(True, nc) called
                Register navigation, menus, jobs...
                Return "" on success
```

## AppAPI authentication — how requests are verified

Every request from AppAPI to your ExApp carries four authentication headers:

| Header | Content |
|--------|---------|
| `AA-VERSION` | Minimum AppAPI version your app requires |
| `EX-APP-ID` | Your app's ID (`pinboard_python`) |
| `EX-APP-VERSION` | Your app's current version |
| `AUTHORIZATION-APP-API` | Base64-encoded `userid:secret` |

`AppAPIAuthMiddleware` validates all of these automatically on every request. It checks that the app ID matches, that the secret in `AUTHORIZATION-APP-API` matches the shared secret set during registration, and that the request is coming from a known AppAPI instance.

This is why you can't hit your ExApp endpoints directly from a browser during development — requests without valid AppAPI headers will be rejected with 401. For testing endpoints you'll use the registration and enable flow, or write proper test code that provides the headers.

> **The shared secret** is the `APP_SECRET` you set in your environment variables and the `"secret"` field in the `app_api:app:register` JSON. They must match exactly. Choose something random — during development `12345` or a simple string is fine, but use a proper random value in production.

## The Makefile

Developing ExApps involves repeating the same terminal commands constantly: start the server, register with AppAPI, test, stop, unregister, edit, repeat. A `Makefile` wraps all of this so you can type `make run` and `make register` instead.

Create `Makefile` in your project root:

```makefile
# SPDX-FileCopyrightText: 2025 Your Name
# SPDX-License-Identifier: AGPL-3.0-or-later

.DEFAULT_GOAL := help

APP_ID      := pinboard_python
APP_PORT    := 23000
APP_SECRET  := pinboard_dev_secret
APP_VERSION := 0.1.0
NEXTCLOUD   := master-nextcloud-1

.PHONY: help
help:
	@echo "Pinboard ExApp development commands"
	@echo ""
	@echo "  make run        Start the FastAPI development server"
	@echo "  make register   Register app with AppAPI (manual_install daemon)"
	@echo "  make unregister Remove app registration from AppAPI"
	@echo "  make restart    Unregister, then register again"

.PHONY: run
run:
	APP_ID=$(APP_ID) APP_PORT=$(APP_PORT) APP_HOST=0.0.0.0 APP_SECRET=$(APP_SECRET) APP_VERSION=$(APP_VERSION) AA_VERSION=2.0.0 NEXTCLOUD_URL=http://nextcloud.local python3 ex_app/lib/main.py

.PHONY: register
register:
	docker exec $(NEXTCLOUD) sudo -u www-data php occ app_api:app:unregister $(APP_ID) --silent --force || true
	docker exec $(NEXTCLOUD) sudo -u www-data php occ app_api:app:register $(APP_ID) manual_install \
		--json-info "{"id":"$(APP_ID)","name":"Pinboard","daemon_config_name":"manual_install","version":"$(APP_VERSION)","secret":"$(APP_SECRET)","port":$(APP_PORT)}" \
		--force-scopes \
		--wait-finish

.PHONY: unregister
unregister:
	docker exec $(NEXTCLOUD) sudo -u www-data php occ app_api:app:unregister $(APP_ID) --silent --force || true

.PHONY: restart
restart: unregister register
```

### What the Makefile does

**`make run`** — sets all required environment variables inline and starts uvicorn. Equivalent to the manual `export APP_ID=...` + `python3 main.py` sequence from B-01, but one command.

**`make register`** — unregisters the app first (`|| true` means "don't fail if it wasn't registered"), then registers it fresh. This handles the common case where you're re-registering after a code change. Note it uses `docker exec master-nextcloud-1` directly — this is the standard pattern in the ExApp ecosystem for docker-dev.

**`make unregister`** — clean removal with `--silent --force` so it doesn't fail if the app isn't currently registered.

**`make restart`** — shortcut for the most common development action: unregister, then register again, which triggers a fresh `enabled_handler` call.

> **`NEXTCLOUD := master-nextcloud-1`** — this is the container name in `nextcloud-docker-dev`. Verify yours with `docker ps | grep nextcloud`. It may be `nextcloud-nextcloud-1` depending on your setup.

## Common problems

**`make: docker: command not found`**  
Docker isn't in your PATH or isn't running. Make sure Docker Desktop is open (Mac/Windows) or the Docker daemon is running (`sudo systemctl start docker` on Linux).

**`docker exec: no such container master-nextcloud-1`**  
Your container has a different name. Run `docker ps | grep nextcloud` to find it and update `NEXTCLOUD := ` in the Makefile.

**`make register` times out waiting for ExApp**  
Your server (`make run`) isn't running in another terminal, or is running on a different port. The `APP_PORT` in the Makefile and the port in the JSON must match.

**`info.xml` schema validation fails**  
The schema URL in the `xmlns:xsi` declaration validates against the app store schema, which may not recognise the `<external-app>` block from older schema versions. If `xmllint` reports an error on `<external-app>`, that's expected — the schema is for the store validator, and ExApp manifests extend it.

**`enabled_handler` returns an error string**  
Check uvicorn's terminal output — Python exceptions during `enabled_handler` are printed there. Common cause: trying to make a user-context nc_py_api call (file operations, preferences) during enable, when no user is active.
